# 方案(grilling):远程/本地文件面板行为一致性 —— 「会话文件系统视角」架构

**日期**:2026-09-17
**状态**:**已裁决并实施完成(v0.4.0,ADR-043)** —— 开发者裁决:daemon Windows/Linux 双平台都要;SSH 采用零依赖路线(系统 ssh + ControlMaster + 反向隧道,不引 ssh2);requestActivation 自动展开折叠右栏;四支柱一次全做。实施记录见文末「§7 实施落点」。
**触发**:开发者反馈「远程使用 Marina,文件访问表现与本地不一致:①『已打开』标题没有 (N) 数量徽章;② AI 打开文件后不自动跳转;③ 终端里文件路径链接点击不打开。认为是架构问题,要求一劳永逸。」

---

## 1. 背景与已定结论(自包含,供任何 session 打开都能读懂)

### 1.1 已核查、不动的架构事实

- **ADR-042(2026-09-14)**:Android 客户端 = Capacitor WebView 壳,**复用完整桌面 renderer 源码**(`apps/mobile/vite.config.ts` 把 `@renderer` alias 到 `src/renderer`);协议单一真相源在 `src/shared/protocol.ts`(142 命令 + 31 事件);main 侧本地 IPC 与 WS 远程**共享同一张 handler 表**(`src/main/ipc.ts` 的 `dispatchCommand` 从 `registerHandle` 同一张表取 handler)。→ 远程**不缺 UI、不缺协议、不缺 handler**。
- 三个功能在 renderer 和协议层完全共享,本地远程跑的是**同一份代码**。差异全部来自 main 侧的数据与通道假设,详见 §1.2。
- 本地链路(已验证工作)作为对照基准:
  1. **徽章**:main 侧 `FilePanelService`(唯一状态源)任何变化 → `evt:file-panel:updated` 广播 → renderer `store.tsx:1119` 收进 `appState.filePanels` → `LayoutHost.tsx:153-157,427` 算出 `已打开 (N)`。
  2. **AI 打开 → 跳转**:PTY spawn 时注入 `MARINA_SERVICE/MARINA_TOKEN/TERMINAL_ID` 环境变量(`session-manager.ts:1084-1095`)→ agent 子进程 POST `127.0.0.1` 的 `LocalHttpGateway` `/open-file` → `FilePanelService.openFile` → `emitUpdated(requestActivation=true)` → 广播 `evt:file-panel:updated` → reducer(`store.tsx:562-575`)把活动面板切成「已打开」→ FileViewer 渲染 activePath。
  3. **终端链接点击**:xterm link provider 检出路径 → `cmd:file-panel:open` → **同 2 的后半段**(openFile → 跳转)。

### 1.2 三个症状的精确根因(五条,证据均为本次核查)

**名词定义**:「daemon」= 跑 Marina main 进程的机器(本地模式 = 你的 PC;远程后端模式 = 服务器)。「客户端」= 任何一个看终端的窗口(本地 Electron 窗口 / 桌面远程窗口 / Android App)。「session 的文件系统」= 该终端里进程所认为的文件世界(本地 PTY = daemon 的 fs;SSH 会话 = 远端主机的 fs)。

| 症状 | 根因 | 证据 |
|---|---|---|
| ① 远程无 (N) 徽章 | **A. 快照缺口**:`cmd:app:get-snapshot` 返回的 `AppSnapshot` **不含 filePanels / commandPanels**。任何「新连接的客户端」这两块状态从零开始,徽章无从渲染;只有用户手动点开过「已打开」面板(mount 时 `cmd:file-panel:get-open-files` 拉一次)或恰好有活事件到达才补上。Android 每次冷启动和断线重连都 `location.reload()` 重走 boot(`apps/mobile/src/main.tsx:385-388`),**永远是新客户端**。本地窗口通常一直活着收广播,掩盖了这个缺口——其实桌面新开窗口同样没有徽章,只是没人注意。 | `src/main/ipc.ts:3042-3054`(buildSnapshot 字段清单);`src/renderer/components/file-panel/FilePanel.tsx:100-124`(仅 mount 拉取) |
| ② AI 打开文件不跳转 | **B. SSH 上报通道物理断开**:agent 上报地址 `MARINA_SERVICE` 指向 **daemon 机器的 127.0.0.1**。SSH 会话里远端主机的进程到不了这个地址;且 env 只注入给本地的 ssh 客户端进程,不会传到远端 shell。SSH 会话的面板永远不会有内容,更不会有 requestActivation。(若远程 session 是 daemon 本地终端,此根因不成立——见问题 1。) | `src/main/file-panel-service.ts:24-26` 头注释明示「v1 仅实质支持本地终端」;`src/main/session-manager.ts:1084-1090`(env 注入点) |
| ②(叠加)移动端跳转不可见 | **C. 激活不触碰 dock 折叠态**:reducer 的 requestActivation 分支只写 `activePanels/openPanelViews`,**不展开折叠的右栏**。移动端三页布局 dock 默认折叠(`LayoutHost.tsx:140-150,287-299`)→ 即使事件到达、状态切换,用户也看不见。桌面端 dock 平时展开所以「看得见切 tab」。 | `src/renderer/store.tsx:556-575`;`LayoutHost.tsx:266-269`(注释明言无自动展开 effect) |
| ③ 链接点不开 | **D. SSH 会话被显式裁剪**:SSH 会话**不注册**文件路径 link provider;markdown 链接在 SSH 下只保留 http/marina: 类。理由写在代码注释里:「裸路径在本机(daemon fs)不可达,点了必 toast」。 | `src/renderer/components/TerminalView.tsx:1469-1471`(isSshSession 不注册)、`:1527`(md 链接过滤) |
| ③(同源) | **E. 读取层假设本地 fs**:`FilePanelService` 全部用 node `fs` 在 daemon 本机 `resolveAndStat/read/watch`。SSH 远端路径必然失败。D 是 E 在 UI 侧的预防性遮蔽——先有 E 才有 D。 | `file-panel-service.ts`(fs 引入 + openFile/read 全本地);SSH `currentCwd` 是远端路径 |

### 1.3 一句话诊断

FilePanel 子系统建立在**三个隐含假设**上:

1. 「session 的文件系统 = daemon 的本地 fs」(根因 E,衍生 D)
2. 「agent 进程与 daemon 共享 localhost」(根因 B)
3. 「客户端活着、广播能追平状态」(根因 A,叠加 C)

本地窗口 + 本地 PTY 下三条全真;任何远程形态至少破一条。**三个症状不是三个 bug,是同一类 bug(「daemon 本位」假设)在三个功能上的投影。** 逐个打补丁会继续在第四、第五个症状上复发;一劳永逸 = 把三个假设逐个变成显式的、无远端近端之分的机制。

## 2. 方案总览:四个支柱

| 支柱 | 治什么 | 一句话 |
|---|---|---|
| **P1 SessionFs 会话文件系统层** | 根因 E + D | main 引入 per-session 文件访问抽象(本地会话 = node fs;SSH 会话 = 系统 ssh 复用 ControlMaster 一次性读);FilePanelService 与链接解析全部走该层;SSH 会话解除 link provider 禁用 |
| **P2 上报通道可达** | 根因 B | SSH 会话 launch 参数加 `-R` 反向隧道把 daemon 的 LocalHttpGateway 端口转发到远端 loopback;`MARINA_SERVICE/MARINA_TOKEN/TERMINAL_ID` 经**远端命令行 env 前缀**注入(不依赖 sshd AcceptEnv)。gateway 仍是唯一入口,零新协议 |
| **P3 快照补齐** | 根因 A | `AppSnapshot` 纳入全部 session 的 filePanels + commandPanels(PROTOCOL_VERSION 4→5),新客户端冷启动即有徽章 |
| **P4 激活可见性** | 根因 C | requestActivation 到达且右栏折叠 → 自动展开(移动端 = 滑入右页),桌面移动同规则 |

症状 × 支柱覆盖:① ← P3;② ← P2(数据)+ P4(可见);③ ← P1。四个支柱相互独立,可分期(见问题 5)。

### 支柱 P1:SessionFs(架构核心)

**现状**:`FilePanelService` 直接 `import node:fs`;SSH 会话在 UI 层(TerminalView)被整体遮蔽。
**改法**:main 新建 `SessionFs` 接口(`stat(path)` / `readFile(path, {maxBytes})` / `resolve(base, rel)`),按 session 类型提供两个实现:

- `LocalSessionFs`:现 node fs 路径原样搬入(行为零变化)。
- `SshSessionFs`:一次性 `ssh -o ControlPath=... user@host -- 'stat ... / head -c N file'`(二进制 base64)。**ControlMaster 默认已开启**(`settings-manager.ts:104`),复用控制连接单次延迟约 50-200ms,无重握手。远端仅假设 POSIX 工具(stat/head),Windows 远端主机读取失败走「打不开」toast,与文件不存在同一路径。

**renderer 侧**:删除 `isSshSession` 对路径 link provider 的禁用与 md 链接过滤(`TerminalView.tsx:1469-1471,1527`)。点击 → `cmd:file-panel:open` → main 经 SessionFs 在**session 自己的 fs** 里解析。链接点击/面板操作仍要求 claim 该 session(ADR-042 裁决 2「单流」不变)。
**降级边界**:SSH 会话**不做**远端文件变更 watch(SFTP 也无 inotify,ssh2 同样做不到推送)——自动刷新降级为「面板激活/切文件时 stat 比对 mtime + viewer 手动刷新」,与本地「fs.watch 推送」存在体感差,但「打开/查看/跳转」完全一致。

### 支柱 P2:上报通道(SSH 反向隧道 + 远端命令 env 前缀)

**现状**:env 注入只对本地 PTY 生效;SSH 远端进程拿不到地址也到不了 127.0.0.1。
**改法**(两处,全在 `buildSshLaunchParams` / `buildRemoteLoginCommand` 一条链上):

1. ssh 参数追加 `-R 127.0.0.1:<remotePort>:127.0.0.1:<gatewayPort>`(每 session 从私有区间如 32900-32999 取位;`ExitOnForwardFailure=no`,转发失败不杀终端,上报静默降级——agent 脚本本就有 `/health` 探活)。远端绑定 loopback(sshd 默认 `GatewayPorts=no`),继续要求 Bearer token,安全面与现状同级。
2. 远端登录命令前缀 `export MARINA_SERVICE=... MARINA_TOKEN=... TERMINAL_ID=...; cd ...; exec $SHELL -l`——**任意 sshd 可用**,不碰 AcceptEnv。

gateway、token、`show-in-marina` 脚本、协议**零改动**——对 agent 来说「上报地址」从永远不可达变成永远可达。
**已知边界**:tmux `attach-or-create` 模式 attach 到**已存在**的 tmux server 时,pane 内进程是老 server 的子孙,新 env 不会重放 → 该场景上报绑定不到本终端。v1 接受降级(与现状持平,现状是完全不可用);`new` 场景全功能。备选通道方案对比见问题 2。

### 支柱 P3:快照补齐

`GetSnapshotResponse`(即 `AppSnapshot`)增加 `filePanels: FilePanelSnapshot[]` 与 `commandPanels: CommandPanelSnapshot[]`(全部 session,main 侧唯一状态源直接序列化);renderer boot 时灌入 store;`PROTOCOL_VERSION` 4→5(按 ipc-protocol.md §10 演进流程,客户端与 daemon 同版本发布)。同时天然修掉「桌面新开窗口无徽章」的同源小病。

### 支柱 P4:激活可见性

`file-panel/updated` 带 `requestActivation` 且该 session 右栏折叠 → 展开(桌面 = 展开右栏;移动端 = 滑入右页)。仅作用于**当前正在看**的 session(与现状一致,不抢 session 切换)。产品裁决见问题 4。

## 5. 待裁决问题

> 依赖关系:问题 2、3、4 相互独立;问题 5 依赖问题 1。**问题 1 是事实确认,优先回答**;P3/P4 无条件正确,问题 1 的答案不阻塞它们开工。

### 问题 1(事实确认):你远程使用时,session 是哪种形态?

- **上下文**:根因 B/D/E 只在「SSH 会话」下成立;根因 A/C 对任何远程客户端都成立。这决定第一期要不要做 P1/P2 主体。
- **推理链**:你报告「链接点不开」——若远程 session 是 daemon 本地终端,link provider 是注册的、`cmd:file-panel:open` 在 daemon fs 上也该成功;只有 SSH 会话才被 `TerminalView.tsx:1469` 整体禁用。所以推断你的远程 session 大概率(至少部分)是 SSH。但 Android → PC(本地 PTY)拓扑下症状 ① 仍应出现(快照缺口),② 在移动端也可能只是「看不见」(根因 C)——无法从你的描述排除。
- **待裁决**:远程连接的 daemon 跑在哪(PC 还是 Linux 服务器)?终端 session 是「daemon 上的本地 shell」还是「SSH 到别的机器」,还是两者都有?
- **我的推荐/预期**:两者都有(以 SSH 为主)。方案按 SSH 设计——它是上界,覆盖它则本地终端自然被覆盖。

### 问题 2(支柱 P2 选型):SSH 会话的 agent 上报通道,用反向隧道还是别的?

- **上下文**:要让「AI 打开文件」在 SSH 会话工作,远端 agent 进程必须能把「打开请求」送到 daemon。候选三条路:
  1. **SSH `-R` 反向隧道 + 远端命令 env 前缀**(§2 P2 所述):gateway 不动、脚本不动、零新依赖。缺点:tmux attach 已有会话时 env 不重放(接受降级);每 session 占一个远端临时端口。
  2. **OSC 字节流上报**:agent 脚本向 stdout 写自定义 OSC 序列,daemon 的 PTY 输出解析器截获(与 cwd 跟踪 OSC 1337 同机制),无网络。缺点:**tmux 模式下 OSC 默认被 tmux 吃掉**(passthrough 包装历史经验不可靠,Marina 的 SSH tmux 支持是正式功能);解析器漏接时序列会污染终端画面;heading/行号等参数在转义序列里编码别扭。
  3. **引入 ssh2 库**内嵌连接 + 自定义 channel:能拿到常驻双向通道,但新 npm 依赖(见问题 3 的边界 2 问题),且与现有「系统 ssh + ControlMaster」体系并存两套连接管理。
- **待裁决**:选 1 / 2 / 3?
- **我的推荐**:**选 1**。改动集中在一个函数族(`buildSshLaunchParams`),复用已验证的 gateway + 脚本生态,tmux 边界明确可控;2 的 tmux 缺陷对这个项目是硬伤;3 的收益(常驻通道)目前只有上报一个消费者,不值两套连接体系。

### 问题 3(支柱 P1 选型):SSH 会话的文件读取层,系统 ssh 还是 ssh2 库?

- **上下文**:SessionFs 的 SSH 实现要能 `stat` 和读文件内容。候选:
  1. **系统 ssh + ControlMaster 一次性命令**(默认已开启连接复用,单次 50-200ms):`stat` 拿 mtime/size,`head -c <max> | base64` 拿内容。零新依赖,和 SSH 会话本体同一套二进制/同一套认证(包括跳板、agent、key 全部白得)。
  2. **引入 `ssh2` npm 包**(内嵌 SSH 协议实现 + SFTP):常驻连接、标准 API、二进制读取干净。代价:新 npm 依赖且带 native 构建(**边界 2,必须你拍板**);要自管认证/跳板/known-hosts,等于在系统 ssh 之外再造一套连接层;SFTP 同样没有远端 inotify,「watch 缺失」的降级与方案 1 一模一样。
- **待裁决**:选 1 还是 2?(选 2 = 批准新增依赖 `ssh2`。)
- **我的推荐**:**选 1**。文件查看是人点的动作,100ms 级延迟无感;唯一的重复成本是每次读起一个 ssh 进程,ControlMaster 下就是一次本地 fork。将来若出现高频读取场景(比如远端目录树面板),再评估迁移。

### 问题 4(支柱 P4 产品行为):requestActivation 要不要自动展开折叠的右栏(移动端 = 全屏滑入右页)?

- **上下文**:桌面端 dock 平时展开,「切 tab」天然可见;移动端三页布局右栏默认折叠,当前 reducer 只切 tab 状态,**跳转对用户不可见**(根因 C)。要一致,就需要「激活时展开」;但移动端展开 = 从终端页全屏切到右页,如果你正在终端里打字,这个接管是打断性的。
- **待裁决**:(a) 自动展开,两端同规则(推荐);(b) 移动端不自动展开,改为徽章高亮 + 一次性 toast「AI 打开了 xxx [查看]」,桌面端照旧;(c) 其他。
- **我的推荐**:**(a) 自动展开**。理由:「AI 打开文件」的产品语义就是「请你看这个文件」(软件定义书 file-panel 的 program-push 模型),静默不展示违背功能本意;打断顾虑成立时用户可以再滑回来,一次滑动手势成本低于永远看不见。若实测觉得打断感强,可再退到 (b),实现成本都很小。

### 问题 5(依赖问题 1):分期与顺序?

- **上下文**:P3/P4 是纯增量小改(一个快照字段 + 一个展开 effect),对所有拓扑立即见效;P1/P2 是架构主体(新抽象层 + ssh 启动链改造 + renderer 解禁),体量约等于当年「SSH 完整支持」的一个阶段。
- **待裁决**:是否按 **P0 = P3+P4(一个 checkpoint)→ P1 期 = P2+P1(一个 checkpoint)** 推进?若问题 1 答案是「远程全是 daemon 本地终端」,P1 期是否降级为储备(先不做)?
- **我的推荐**:按上述两期推进;若拓扑确认含 SSH(预期如此),两期都做,完成后本地/远程在「徽章 / 跳转 / 链接」三个行为上端到端一致,并有 parity 测试兜底(loopback 测试扩展:SSH 会话模拟 + 快照字段断言)。

## 6. 边界与明确不做(本方案范围内)

- SSH 远端文件**不做**变更 watch 推送(技术上不可行),降级为激活时 stat 比对 + 手动刷新。
- HTML 预览 `marina-file://` 维持 ADR-042 已裁决的远程降级,不在本方案。
- 不依赖 sshd 的 `AcceptEnv`(env 走远端命令前缀,任意默认 sshd 可用)。
- tmux attach 已有会话:上报 env 不重放,v1 接受降级(见支柱 P2 边界);tmux new 场景全功能。
- 远端为 Windows 主机:POSIX stat/head 不可用 → 读取失败走「打不开」toast,与文件不存在同路径,后续如有真实需求再议。
- 链接点击 / 面板操作仍要求 claim session(单流语义,ADR-042 裁决 2,不变)。
- 不引入「观察流 / 输出多播」(ADR-042 明确不做,本方案不触碰)。
