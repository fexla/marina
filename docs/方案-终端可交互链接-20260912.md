# 方案:终端可交互内容增强(pi bridge 插件检测 + OSC 8 渲染 + []() 解析)

- **日期**:2026-09-12
- **状态**:已实现(见文末验证)
- **归档**:软件定义书 ADR-040、CHANGELOG `[Unreleased]`
- **触发**:开发者指示 ——「增强终端正文的可点击内容;pi bridge 场景下把链接/文件
  路径检测移到插件侧(Marina 不再做检测),解决换行导致检测不出的问题;pi 展示的
  信息可以把长链接替换成可点击样式;插件告诉 Marina 哪段字符可交互、交互内容是
  什么;新增 `[]()` markdown 解析,逻辑对齐 markdown 面板(含 Marina 扩展)」。

---

## 0. 背景与问题

v0.3.3 的终端可点击内容 = renderer 里两个 xterm link provider,对 **buffer 行文本**
跑正则(ADR-027):

| Provider | 检测对象 | 换行表现 |
|---|---|---|
| WebLinksAddon(官方) | http(s) URL | 跨折行感知(官方 `_getWindowedLineStrings` 拼接) |
| 自研文件路径 provider | `src/x.ts:42` 形态(STRICT 正则) | **只读单行** → 路径被软折行劈断即检测不出 |

自研 provider 的单行检测是 ADR-027 的实现盲区;而 pi 的输出(助手消息、思考块、
工具结果)恰恰充满长路径和长 URL,折行劈断的链接在体感上就是「时灵时不灵」。

## 1. 关键调研结论(全部对照源码验证)

1. **pi 0.85.1 有官方 `pi.registerMarkdownTransformer(fn)`**(types.d.ts :966):
   display-only(不动会话持久化与 LLM 上下文),在 pi 自己的 marked 解析**之前**
   拿到完整 markdown 原文;流式每 chunk / 最终消息 / 恢复会话都会以**原始文本**
   重跑 → transformer 必须纯函数、无 IO。
2. **pi 原生把 `[text](url)` 渲染为 OSC 8 超链接**,但按终端能力白名单检测
   (WT_SESSION / kitty / vscode …),Marina 不在名单 → 回退 `text (url)` 明文。
   **`PI_HYPERLINKS=1` 是 pi 官方的强制开关**。
3. **xterm 6.1.0-beta.256 的 OSC 8 机制**:
   - 不设 `options.linkHandler` 时,非 http(s) 协议的链接(`marina:`)被**整体丢弃**
     (OscLinkProvider 源码:URL 协议白名单检查);设 `linkHandler.allowNonHttpProtocols
     = true` 后 activate/hover/leave 全由 Marina 接管,URI 原样传递。
   - **优先级 = provider 注册序**,OscLinkProvider 构造时注册在首位 → OSC 8 链接
     hover/click 永远赢过自研 provider,重叠的自研命中被 `_removeIntersectingLinks`
     剔除 → **与 Marina 自研检测天然共存,无冲突**。
   - OSC 8 cell 标记天然跨软折行(xterm 写 buffer 时逐 cell 标记)→ 这就是
     「插件侧检测不怕换行」的底层依据。
   - **SerializeAddon 不保留 OSC 8**(逐 cell 只 diff SGR)→ scrollback 回放后旧链接
     退化为纯文本(降级,见 §5)。
4. **Marina 现有资产可复用**:`marina-link.ts`(解析/分词)、`marina-link-dispatch.ts`
   (session 作用域分发)、`MARINA_LINK_RUN` IPC(payload 已含 sessionId)、
   `terminal-path-detector.ts`(STRICT 正则)、heading 导航事件链(requestId 键控)。

## 2. 架构(最终形态)

```
┌─ pi 会话(第一通道:bridge transformer)─────────────────────────┐
│ pi markdown 原文                                                  │
│   → bridge linkify transformer(检测+改写,源文本层,无换行问题)    │
│     · 裸文件路径(vendored STRICT 检测)→ [原文](marina:show "绝对路径" --line N)
│     · 裸 URL → [短标签](url);超长(> max(28, 宽/2))label 缩为域名+尾段 │
│     · fenced code / inline code / 已有链接 / 图片:不透明透传        │
│   → pi marked 渲染 → OSC 8 字节流(依赖 PI_HYPERLINKS=1)           │
│   → Marina osc1337-parser 透传 → xterm buffer(跨折行不断链)        │
│   → hover 下划线 + tooltip / click                                │
│   → linkHandler.activate → terminal-link-router 路由               │
└────────────────────────────────────────────────────────────────────┘
┌─ 非 pi 场景(第二通道:终端级 provider)────────────────────────────┐
│ pi -p 打印模式 / cat md 文件 / 其它工具输出的裸 [label](href)       │
│   → terminal-md-link-detector(shared 纯函数,语义对齐 marked)       │
│   → TerminalView 的 []() provider(跨折行窗口文本上检测)            │
│   → 点击走同一条 router                                            │
└────────────────────────────────────────────────────────────────────┘
┌─ 路由(terminal-link-router.ts,与 md 面板 MdLink 语义对齐)────────┐
│ https?/mailto → SYSTEM_OPEN_EXTERNAL(系统浏览器)                  │
│ marina:       → MARINA_LINK_RUN(session 作用域;show 进本 session   │
│                文件面板,run 命令面板执行;终端来源无 mdPath/cmdKey,  │
│                show 相对 session currentCwd 解析——bridge 已绝对化)  │
│ #anchor       → no-op(终端无文档内导航语义)                        │
│ 其余          → openPathFromTerminal 候选链(FILE_PANEL_OPEN)       │
└────────────────────────────────────────────────────────────────────┘
```

「插件告诉 Marina 哪段可交互」的通道 = **终端流本身(OSC 8 URI,in-band)**,不是
HTTP 注解。理由:URI 随文本落进 buffer,xterm 自己维护 cell ↔ 链接的对应(跨折行、
选中、复制、装饰全部原生正确);HTTP 注解则要求事后文本匹配对齐 buffer 位置,TUI
重绘/resize reflow 下必然漂移。pi 对 marina: URI 的解析路由复用 ADR-035 全套
(main 端 marina-link-dispatch),插件零路由逻辑,符合 bridge「哑转发器」定位。

## 4. 裁决记录(三项默认裁决,AskUserQuestion 未获答复,按推荐执行)

1. **Marina 自研检测在 pi 会话保留共存**(不硬禁用)。依据:OSC 8 优先级自动遮蔽
   重叠命中(§1.3);保留可兜底 pi -p 打印模式、pi 前后的 shell 混排输出、以及
   scrollback 回放后 OSC 8 退化(§5)的场景。
2. **`[]()` 解析双通道**:pi TUI 走插件 transformer;另加终端级 provider 覆盖裸
   markdown 文本。顺带用跨折行工具升级文件路径检测,非 pi 终端也修好换行问题。
3. **终端 marina:run 无确认执行**,信任模型同 ADR-035(与 md 面板一致);hover
   tooltip 始终展示命令原文(知情点击),执行在命令面板可见可停。已知外延:OSC 8
   是字节流,任何程序输出都能伪造 marina: 链接 —— 但终端本就是任意代码执行面
   (输出同样能诱导用户手敲命令),不引入新的暴露;show 只读无风险。

## 5. 已知降级与取舍

- **scrollback 回放后 OSC 8 链接退化**:SerializeAddon 不序列化超链接 → 视图重建
  (generation 切换 / LRU 逐出)后旧链接变纯文本。兜底:自研 provider(文件路径 +
  URL + []())对回放文本照常检测,marina: 动作语义丢失(可接受;v2 可做 serialize
  补丁重发 OSC 8)。注意 TerminalDeck 的 parked 实例(≤10)不重建,链接原样存活。
- **老 pi(无 registerMarkdownTransformer)**:typeof 守卫静默跳过;pi 原生
  `[]()`→OSC 8(PI_HYPERLINKS=1)仍生效,仅裸路径检测缺失。
- **纯反斜杠 Windows 路径(`D:\x\y.ts`)不检测**:STRICT 规则要求正斜杠(防盘符/
  注册表键误报,ADR-027 实证);bridge 与终端检测行为一致。
- **`array[i](x)` 紧贴形态会命中 []() 检测**:与 CommonMark/marked 行为一致(markdown
  里它本来就渲染成链接),不为终端收紧;误点代价 = 路径不存在 toast。
- **md 文件 + `--line`**:忽略 line 照常打开(markdown 渲染输出与源码行号无对应,
  md 的导航语义是 --heading);bridge 对任何 `path:123` 都生成 --line,不因此断链。

1. `npm run dev`,开一个终端 session。
2. **通道一(需 pi)**:终端里跑 `pi`,问一个会输出长路径的问题(比如「列出本仓库

4. **折行**:把窗口拉到很窄重复 2/3,链接跨行仍可点(文件路径检测已升级跨折行)。
5. **marina: 动作**:终端里让 pi(或手写 markdown)`[打开](marina:show%20package.json)`,
   点击 → 文件面板打开 package.json;`--line` 形态跳行。

## 8. 折行链路审计(2026-09-12 追加,开发者问询触发)

场景:AI 写了一个表格,某行太长,pi 渲染时自动折行,把单元格里的链接劈开。
逐段核查(方法:pi-tui 源码 + 真实探针[node 直接 import pi-tui 渲染并检查输出
字节流] + xterm 源码):

| 链路段 | 结论 | 证据 |
|---|---|---|
| ① transformer 拿原始内容 | ✅ 拿的是 markdown 源文本;表格行在源里是**一行**,检测在源层,与渲染折行无关 | pi registerMarkdownTransformer 语义(display-only,marked 解析前) |
| ② 表格单元格里的链接 | ✅ 单元格走完整 inline token 渲染,`[t](u)` 照常产出 OSC 8 | pi-tui markdown.js :689/:695/:767(renderInlineTokens)→ :529-550(link 分支 → hyperlink()) |
| ③ pi 折行劈开 OSC 8 | ✅ **关键段,实测通过**:AnsiCodeTracker 在折行边界显式关闭 + 携完整 URI 重开;词折行与超长词拆分两条路径都覆盖;表格 wrapCellText 走同一管道 | pi-tui utils.js :444-666/:787-932;探针:120 字符链接 width=40 → 3 行,每行行首 `\x1b]8;;<完整URI>` 重发、行尾关闭;超宽表格(width=80,~125 字符链接单元格)→ 折 2 行,同样逐行重发 |
| ④ 表格超宽 | ✅ 折行不截断(列宽收缩算法);唯一退化:终端 < 3n+1+n 列(2 列表即 <9 列)时回退 raw markdown,链接变字面量 | markdown.js :666-809(无 truncate 调用)、:676-683(极端窄回退) |
| ⑤ xterm 解析预折行 | ✅ pi 预折的每个物理行含完整开/闭序列,各自独立成链(同一 URI),劈成的两段**都可点** | xterm InputHandler.ts :3122-3145(urlId 按 cell 写入) |
| ⑥ 若 pi 输出未折行超长行(xterm 软折) | ✅ 软折行不重置 parser 属性,续行 cell 同 urlId;OscLinkProvider._getRangeWithLineWrap 沿 isWrapped 拼回完整 range,hover 第二行尾巴也能命中正确 URI | InputHandler.ts :575-598;OscLinkProvider.ts :108-173;Linkifier.ts :370-374(线性坐标命中) |
| ⑦ resize reflow | ✅ 拆/并行走 copyCellsFrom 逐 cell 复制 extended attrs,urlId 不丢;旧版 reflow 丢链接的 bug 在 6.1.0-beta.256 不存在。**小边缘**:光标行默认不参与 reflow(reflowCursorLine=false),光标行上超新宽度的链接会被截尾(截的是内容本身) | BufferLine.ts :506-537;Buffer.ts :263-272;OptionsService.ts :50 |
| ⑧ scrollback 裁剪 | ✅ OscLinkService 按 marker 引用计数,链接部分滚出 → 尾部行 marker 仍在 → 剩余段仍可点、URI 正确;全滚出 → 条目清理无泄漏;失效 urlId 静默跳过不报错 | OscLinkService.ts :30-101;Buffer.ts :645-651 |
| ⑨ 点击事件 | ✅ URI 按 linkId 从 OscLinkService 取,与命中哪一段无关 → Marina linkHandler.activate 拿到完整原始 URI | OscLinkProvider.ts :59-62 |

**总评**:链路无断点。用户最担心的「劈成两段后点击」实际形态是——pi 折行产出的
两个物理行各自携带**完整的开/闭序列和完整 URI**,是两段各自完整的可点链接指向
同一目标,不存在"半截链接"。已知降级仍是 §5 的 serialize 回放(旧链接退化纯文本)
与本节新记录的两个边缘(终端 <9 列的表格 raw 回退、光标行 resize 截尾)。
