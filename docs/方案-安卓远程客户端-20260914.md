## 背景与已定结论(自包含上下文)

开发者指令(2026-09-14 原文):

> 开始 0.3.4。首先是做一个安卓端的 Marina,**只能远程访问 Marina**(即 Android 端
> 不跑本地终端,纯客户端)。交互逻辑在 PC 端的基础上适配手机和平板的比例。

**已经定了的**(不再重复问):

1. **Android 端是纯远程客户端**。没有本地 PTY、没有本地 session、没有 SSH——
   它只是"连接某个 Marina daemon 的观察窗 + 输入通道"。
2. **复用现有远程后端协议**。0.3.3 的远程后端模式(ADR-014/015)已落地:daemon
   监听 WebSocket(默认端口 32780-32789)、token 认证、断线重连 + 10s 宽限 +
   心跳检出。PC 上的"远程窗口"就是这套协议的第一个消费者。
3. **交互以 PC 端为基础适配**,不是重新发明——路径树 / session 状态灯 / 终端 /
   面板这些概念原样保留,只是布局按手机/平板屏幕比例重排。

**本轮技术事实核查结论**(我派探索 agent 全仓核实过,证据都带文件:行号):

- **传输层已经是"纯 WS 协议",对客户端形态零假设**。renderer↔daemon 的通信
  抽象成 `ClientTransport`(`src/main/client-registry.ts:38-53`);WS client 端
  实现 `RemoteTransport`(`src/preload/remote-transport.ts`)的 WebSocket 是
  **注入式适配**(`WSLike` 工厂,`remote-transport.ts:90-91`)——它本来就是按
  "浏览器原生 WebSocket"写的,唯一 Node 依赖是 `node:crypto.randomUUID` 一处
  (`remote-transport.ts:29`),web 环境可换 `crypto.randomUUID`。
- **renderer 代码可以脱离 Electron 构建**。`src/renderer/` 全目录零
  `import 'electron'`、零 `node:` 模块、零 `window.require`;构建配置是标准
  Vite+React(`electron.vite.config.ts:154-190`)。真正的 Android 障碍只有三个:
  ① `window.api` 门面(preload 注入,约 140 处调用 / 25 个文件)——Android 需要
  一个 web 版 shim;② `marina-file://` 特权协议(HTML 预览,`src/shared/web-file-url.ts`)
  ——Android WebView 没有这个协议;③ `queryLocalFonts`——已有 fallback,不是障碍。
- **"远程 client 上限 1"只是规范文字,实现里没有限制**。多个远程 client 并存
  是刻意支持的(`src/main/remote-daemon.ts:189-196` 注释明说"每个远程窗口各自
  持有 clientId,不能用单一 boundClientId");竞争发生在 session 认领层
  (`SessionAlreadyOwned`,`src/main/session-manager.ts:1469-1483`)。daemon 的
  in-process 本地窗口与任意多远程 WS client 并存(`src/main/index.ts:820-822`)。
- **xterm.js 是 6.1.0-beta.256 全家桶**,代码里没有任何触屏配置——终端触屏
  滚动/选择是 Android 端要新做的适配点。

**名词定义**(下文反复出现):

- **daemon**:跑在 PC 上的 Marina 主进程,持有所有 PTY 和数据(§14.9)。
- **client**:连接 daemon 的 UI 端。PC 本地窗口(in-process)和远程窗口(WS)
  是现有两种;Android 端将是第三种。
- **owner / 持有**:一个 session 同一时刻只有一个 client 持有输入权(ADR-005
  单 owner 模型)。非 owner 只能看到 session 存在(灰显),**看不到终端内容**。
- **观察窗**:client 的定性——它不持有数据,关掉不影响任何 session。

## 问题 1:技术栈路线(根问题,问题 5/6/7 依赖它)

### 背景与推理

Android 客户端的本质 = **renderer(React + xterm.js)+ WS 传输 + Android 壳**。
基于上面的核查,renderer 和 WS client 代码都几乎是"web ready"的,所以真正的
决策是:**Android 壳用什么技术,UI 层复用多少**。四个候选:

**A. Capacitor(WebView 壳,复用现有 renderer 源码)**
把 `src/renderer/` 作为共享源码,构建出一份纯 web bundle 装进 Android
WebView 壳;写一个 web 版 preload shim(实现 `window.api.invoke/on` 的 WS
版本,复用 `remote-transport.ts` 的帧协议/重连逻辑)。
- ✅ 复用最大化:面板系统、Markdown 渲染、主题、链接检测……全部白拿;
  PC 与 Android 的交互演进天然同步(同一份代码)。
- ✅ `remote-transport.ts` 的浏览器 WebSocket 适配就是为这种场景写的。
- ✅ xterm.js 在 Android WebView 能跑(Termius 等终端 app 有 WebView+xterm 先例)。
- ⚠️ 需要把 renderer 里残留的桌面假设清理掉(窗口标题栏、`windowDefaults`、
  queryLocalFonts 已有 fallback 等),按屏幕比例做响应式布局。
- ⚠️ 新依赖:Capacitor npm 包 + Android SDK/Studio 工具链(边界 2,需你批准)。

**B. React Native / Expo**
UI 层用 RN 重写,终端用 WebView 内嵌 xterm 或 react-native 终端组件。
- ✅ 原生控件体验(滚动/键盘/手势是系统级的)。
- ❌ 终端渲染是 RN 的弱项:xterm.js 装不进 RN 的非 WebView 环境,社区终端
  组件质量参差;而终端恰恰是本产品的主体。
- ❌ renderer 的全部 UI 资产作废,双端双写。

**C. Flutter / D. Kotlin 原生**
- ❌ 与现有 TypeScript 代码库彻底分裂,协议层要手写第二份客户端实现;
  双端功能永远不同步。对一个单人项目是维护灾难。

**E. 纯 Web UI(daemon 内置 HTTP 静态服务,手机浏览器直接访问 / PWA)**
不装 app,daemon 起一个 HTTP server 服务同一份 web bundle。
- ✅ 零安装、零商店审核,连 iOS 都顺带覆盖。
- ❌ **正面撞 ADR-014 的"不做 Web UI(V2 候选)"**;浏览器标签页的终端
  体验(键盘工具条、全屏、后台保活)明显弱于 app 壳;通知/分享系统集成缺失。

### 待裁决点

选哪条路线?(若选 A,等于启动 ADR-014 里"Web UI V2 候选"的对应部分,我会
在软件定义书里为 Android 客户端新开一节 + 新 ADR,把"只 Electron client"
修正为"Electron client + Android client"。)

### 我的推荐 + 理由

**A(Capacitor)**。理由:renderer 是这个项目最大的资产,Android v1 的核心
诉求是"能看能点能输入",A 是唯一不分裂代码库的路线;终端主体决定 RN 路线
先天残缺;E 可以作为 A 的免费副产品以后再加(app 壳和 web bundle 本来就是
同一份产物),但 v1 不做。

## 问题 2:多 client 并存 + 「只读观察流」要不要做(核心语义问题,独立于问题 1)

### 背景与推理

现有模型(ADR-005):一个 session 同一时刻只有一个 owner;**非 owner 看不到
终端内容**,只能在侧栏看到灰显标签;PC 上点灰显标签 → 聚焦持有它的那个窗口。

Android 的核心使用场景恰恰是:**手机看 PC 上正在跑的 agent**。但按现有模型,
PC 窗口持有 session 时,Android 上它就是灰显的一行——点它?"聚焦 PC 的窗口"
对 Android 无意义(它够不着 PC 的窗口管理器)。也就是说,不加新机制的话,
Android 每次要看一个终端都得先"占用"把它从 PC 手里抢走,PC 那边变灰显——
两个人抢一个终端,体验是灾难。

好在协议/数据层留了口子:ADR-005 当年就写了"协议层留出多 owner 扩展点
(owner 字段设计为 list)";daemon 本来就为每个 session 持有 2MB scrollback
ring buffer(`src/main/session-manager.ts` ManagedSession.scrollback),非 owner
随时可以拉全量历史;ADR-022 的 view lease 机制已经把"输出定向"抽象出来了
(owner 之外的"parked view"已经在接收输出)。

所以选项是:

**a. 维持单流**:Android 想看就抢(占用),不看就放手。实现零改动,体验差。
**b. 只读观察流(输出多播,输入仍单 owner)**:daemon 把 output 事件同时推给
owner(可输入)和任意订阅了该 session 的观察 client(只读);观察者点输入
区 → 提示"此终端由 <某 client> 持有,占用后可输入"(一键占用走已有的
`cmd:session:takeover`)。
- 改动面:`evt:session:output` 从"只发 owner"改为"发 owner + 已订阅观察者";
  新增观察订阅命令;scrollback 拉取对观察者开放(已有 `get-scrollback`)。
  `SessionManager` 的字节流管线本身不动。
- **输入权不变**:ADR-005 的真正动机是"多 owner 输入冲突协调复杂度 5x"——
  我们只多播输出,输入仍是严格单 owner,这条红线不破。
- ⚠️ 带宽注意:手机蜂窝网络下推全量字节流。观察流应默认"追尾模式"
  (只推最新 N KB + 背压丢弃,像 ADR-022 parked view 的做法),而非全量重放。

### 待裁决点

Android v1 是否引入只读观察流?(这同时惠及 PC 多窗口:第二个窗口可以真正
"看"别的窗口持有的终端,而不是只能聚焦跳窗。)

### 我的推荐 + 理由

**做(选 b)**。"手机看 PC 上的 agent"是这个 app 的第一使用场景,没有观察流
Android v1 基本残废;输出多播不动输入单权,ADR-005 的复杂度红线不破;实现面
小(view lease 机制已经是半成品)。若你担心范围,可以裁成"v1 只做 Android
观察、PC 多窗口灰显行为暂不变"。

## 问题 3:网络与安全前提(独立于问题 1)

### 背景与推理

现状(ADR-015):纯 token 认证 + `ws://` 明文,前提是 **WireGuard/内网**——
"用户不经 WireGuard 直接暴露 daemon 端口到公网"是 V1 明确不支持的用法。
token 是 daemon 端 safeStorage 加密的 UUID,可被用户改成好记密码;设置页
只有"设置密码"框,**没有回显/二维码**(全仓 grep 无 qr)。

Android 场景的新变量:手机在 Wi-Fi/蜂窝间切换更频繁(重连体验要扛住);
WireGuard 官方 Android app 成熟可用;手机键盘手输 `host:port + 密码`的配对
体验比 PC 更痛(规范 §14.9.4 本来就设想过"本地 UI 展示 token + 二维码",
实现时砍掉了)。

### 待裁决点

1. v1 Android 是否维持"仅 WireGuard/内网"前提、TLS 继续延后?(
   推荐:**是**,同 ADR-015 的理由原样适用于手机;公网直连需求真出现再上
   TLS+证书指纹。)
2. 配对体验:维持手输,还是 daemon 设置页加"二维码"展示(host+port+token
   编码成一个 URI,手机扫码即填)?二维码需要新 npm 依赖(qrcode 生成库,
   边界 2;或者自绘极简 QR 也就百来行,可以不引包)。(
   推荐:**v1 先手输**,二维码作为 0.3.x 内的体验补强——不为它阻塞主线;
   到时优先评估自绘,避免引包。)

## 问题 4:手机/平板的交互形态(设计确认,依赖问题 1 选 A/B 才有意义)

### 背景与推理

PC 布局(三栏):左侧栏路径树 + 主区(tab 栏 + 终端)+ 右 dock(文件树 /
Git / 已打开面板)。鼠标优先哲学在触屏上是天然盟友(无快捷键依赖),但
三栏在 6 英寸竖屏上放不下。我的适配提案:

**手机竖屏(主战场)**:
```
┌─────────────────┐      ┌─────────────────┐
│ ☰  [终端名 ●]  ⋮ │      │ (抽屉:路径树)    │
├─────────────────┤      │ ▼ ~/projects/x  │
│                 │      │   ├ ● pi 对话    │
│   终端区(全屏)  │      │   └ ◐ shell      │
│                 │      │ ▼ ~/projects/y  │
│                 │      │   └ ● codex      │
│                 │      │ [当前电脑 ▾]     │
├─────────────────┤      └─────────────────┘
│ [Esc][Tab][↑↓←→]│ ← 虚拟键盘辅助键条
│ [系统键盘]      │
└─────────────────┘
```
- 侧栏 → 左缘滑出抽屉(点 ☰ 或左缘右滑);路径树/状态灯原样。
- tab 栏 → 顶栏只显示**当前 session** + 下拉切换(竖屏放不下一排 tab;
  下拉列表 = tab 栏的等价物,仍是"点击切换"无新概念)。
- 右 dock 面板 → 底部上滑 sheet(或顶栏按钮切换);「已打开」面板优先。
- **虚拟键盘辅助键条**:终端在手机上的最大痛点是 Esc/Tab/方向键/Ctrl——
  键盘上方常驻一排可横滑的辅助键(Esc Tab Ctrl ↑ ↓ ← → PgUp PgDn Home End)。
  这不违反 §7.1"不做快捷键"——它们是**按键的触屏等价物**,不是应用内
  功能键(不做 Ctrl+T 开 tab 这类)。
- 手势:长按 = 右键菜单;双指缩放 = Ctrl+滚轮调字号(既有行为);终端内
  拖动选择 = 选中(选中即复制沿用设置)。

**平板/横屏**:空间够,直接用 PC 三栏布局的压缩版(侧栏可折叠、dock 正常)。

### 待裁决点

这个适配方向整体认不认?尤其两个具体点:(1) tab 栏竖屏改"当前终端 + 下拉
切换"可否;(2) 虚拟键盘辅助键条认不认(它是终端可用性的生死线,我认为
必须有)。

### 我的推荐 + 理由

按上述提案做。辅助键条是 Termius/Termux 验证过的标配,没有它手机终端
基本不可用于 vim/交互式程序。

## 问题 5:Android v1 功能范围(依赖问题 1)

### 背景与推理

PC 客户端能力全集:路径树管理(收藏/分组/拖拽)、session 全生命周期、终端、
三面板(文件树/Git/已打开)、设置、模板、多窗口……Android v1 全塞不现实,
要裁剪。我的裁剪提案:

**v1 必做**:daemon 连接管理(增删改 profile、连接/断开/重连状态)、路径树
浏览(含状态灯、⚠️、hasUnviewedWork 警告色)、session 切换/查看(问题 2
的观察流)、终端输入(占用后)、占用/释放、关闭 session、新建 session
(选模板起 agent——手机上"让 PC 上的 agent 干活"是真实场景)。

**v1 建议做**:「已打开」面板(只读看 agent 推的文档/命令输出——这是
Marina 区别于裸终端的核心增值,xterm 小屏看长文档体验差,面板反而是手机
友好的);HTML 预览的 Android 替代方案(WebView 拦截 `marina-file:` 换
`blob:`/`data:` URL,或 v1 降级为源码文本)。

**v1 明确不做**:本地侧任何东西(无 PTY/无 SSH)、设置编辑(只读展示 daemon
设置 + 本机外观少量项——外观归客户端,ADR-029 已定)、文件树/Git 面板
(交互密度高,小屏价值低,v2 再说)、模板编辑、收藏拖拽管理。

### 待裁决点

「已打开」面板进不进 v1?新建 session 进不进 v1?

### 我的推荐 + 理由

「已打开」面板**进**(手机是绝佳的"阅读 agent 产出"终端);新建 session
**进**(命令面窄:选路径 → 选模板,IPC 全现成);文件树/Git 面板 v2。

## 问题 6:工程结构与分发(依赖问题 1 选 A)

### 背景与推理

现状:根 package.json **没有 workspaces**(单包结构);`packages/pi-marina-bridge`
是靠 pi 自己的安装机制工作的独立小包,不走 npm 构建。Android 工程如果走
Capacitor,形态是"一个 npm 包 + Android Studio 工程(Java/Kotlin 壳 + gradle)"。

选项:
- **a. 独立目录独立 package.json**(`apps/mobile/`),共享代码用 tsconfig
  paths 相对引用 `src/shared` 与 `src/preload/remote-transport.ts`,各自构建。
  零风险,不动现有构建链。
- **b. 引入 npm workspaces** 把根改成 monorepo,抽 `@marina/shared` 包。
  更"正规",但动根 package.json/构建链/vitest 配置,回归面大,而且
  electron-builder 对 workspaces 有历史坑。

分发:Play Store 需要开发者账号 + 25 刀 + 审核;**APK 直接装**(GitHub
Release 附 APK,手机浏览器下载安装)零门槛,适合 v1 内部使用阶段。CI
(GitHub Actions Android 构建)可以以后加,先本地构建。

### 待裁决点 + 推荐

**推荐 a + APK 直装**:v1 用 `apps/mobile/` 独立包,不碰 workspaces;
Android SDK 装在你机器上(构建需要,一次性环境成本);产物 APK 走
GitHub Release。Play Store 等 v2 产品稳定后再评估。若你同意,工程结构、
构建脚本、目录约定我出一份更细的施工图作为 0.3.4 的第一份产出。
