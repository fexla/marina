# 方案：终端标题来源分层（TitleSource / TitleResolver）

> 起因：用户报告「运行 pi 的终端，侧栏标题经常显示 `Windows PowerShell` 而不是当前对话标题」。
> 诊断结论：不是解析器丢序列，而是 `displayName` 的**权威模型缺失**。用户判定为架构问题，要求给出架构设计。
>
> 本文是设计方案，**未实施**。定稿后落 ADR-032 + 实施。

---

## 0. 背景与诊断结论（自包含）

### 现象

pi 在 Marina 的 PowerShell session 里运行时，tab / 侧栏标题经常显示 `Windows PowerShell`，
而不是 pi 设置的 `pi - <对话名> - <目录>`。

### 根因链（已验证）

1. **pi 确实发标题**：`ProcessTerminal.setTitle` → `process.stdout.write("\x1b]0;" + title + "\x07")`
   （pi-tui `dist/terminal.js:425-427`），内容 `pi - <sessionName> - <cwdBasename>`
   （pi `interactive-mode.js:756-764`）。Marina 能正常解析与接受。
2. **pi 只在 4 个时机发**：启动后包检查（`:797`）、rebind session（`:1525`）、
   extension UI 清理（`:1736`）、`session_info_changed`（`:2553`）。**对话进行中不重发**。
3. **子进程抢标题**：Windows 上 pi 的 bash 工具 `detached: process.platform !== "win32"`
   （pi `core/tools/bash.js:61`）→ 子进程**共享同一个 ConPTY console**。其中任何
   `powershell.exe` 启动时调 `SetConsoleTitle("Windows PowerShell")`，ConPTY 把它翻译成
   OSC 0 发给 Marina。pi 源码自己承认这个机制：
   > `// On Windows, npm can overwrite the shared console title while checking extension package versions.`
   > （`interactive-mode.js:794-798`，但它只在启动期恢复一次）
4. **Marina 照单全收**：`handleOscTitle`（`session-manager.ts:2317-2325`）是
   last-writer-wins，唯一防线 `looksLikeShellStartupGarbage`（`:2844-2864`）只拦
   *裸路径 / MINGW 前缀 / 裸 `*.exe`* 五条。`Windows PowerShell` 是**友好名**，一条都不命中。
5. **备用通道未激活**：`onPiName`（`:886-894`，不走垃圾过滤）本可纠正，但它依赖 pi 侧装
   Marina bridge 扩展；实测该机 `~/.pi/agent/extensions` 只有 `pi-permission-system` /
   `subagent` → 标题 100% 依赖 OSC，被抢后无人恢复。

### 为什么这是架构问题，而不是过滤规则不够

当前模型把「谁说的话算数」编码在两个错误的维度上：

| 现状编码方式 | 问题 |
|---|---|
| **写入顺序**（last writer wins） | shell 子进程晚于 pi 说话就赢，与权威性无关 |
| **字符串内容**（`looksLikeShellStartupGarbage` 正则） | 要靠猜「这段文字像不像垃圾」，永远列不全（TIT-1 三个月未根治即证明） |

`docs/issues/tit-1-osc-title-shell-startup-garbage.md` 自己写着「这是 workaround，不是根治……
某处一定有过一道我没找到的屏障」。真正缺的不是那道屏障，是**来源身份**：
同一个字节通道（ConPTY OSC 0）混合了两类语义完全不同的发声者 —— 前台程序（pi / vim / claude）
与 shell 及其子进程 —— 而接收端无法区分，只能猜内容。

## 1. 关键洞见：Marina 已经解决过这个问题两次

同一个「多信号源争夺一个字段」的问题，代码库里已有**两个成熟解法**，标题是唯一漏网的字段：

| 字段 | 权威源 | 兜底源 | 协调机制 | 位置 |
|---|---|---|---|---|
| `currentCwd` | OSC 1337 | 定时轮询 | `oscReceived` latch：权威源发声后**永久**关闭兜底 | `session-manager.ts:420-421` |
| `state` (active/idle) | agent 信号（pi） | 字节流启发式 | `TerminalStateGetter` 分层：绑 agent 时字节流**完全旁路**，解绑恢复 | ADR-030 |
| **`displayName`** | **？** | **？** | **无 —— last writer wins + 内容启发式** | ← 本方案要修的 |

ADR-030 的背景段几乎逐字预演了这次对话：

> 根因：session 的 active/idle 判定有两个信号源（pi 明确信号 vs 字节流启发式）**ad hoc 协调**，
> 没有分层。……助手起初 ad hoc 改 settled 立刻 idle，但用户指出**这是架构问题，要求分层重构**。

所以本方案的正确形态不是发明新机制，而是**让标题字段接入代码库已经确立的分层范式**。
这一点决定了下面所有取舍。

## 2. 设计目标与约束

### 目标

1. **来源即权威**：标题的取舍由「谁声明的」决定，不由「谁最后说」或「字符串长得像什么」决定。
2. **消除猜测**：不再需要「这标题像不像垃圾」的内容启发式（至少降级为可选的深度防御）。
3. **可解释**：任何时刻能回答「现在这个标题是谁给的、为什么它赢了」——可日志、可测试、可诊断。
4. **无回归**：`manuallyRenamed`（M1-C）、`clearManualRename`（STM-3）、Claude Code 持续刷标题、
   TIT-1 的裸路径场景，行为全部保持。

### 约束（来自 AGENTS.md / 软件定义书）

- **不改 pi**：pi 是外部包，Marina 端必须自足（pi 侧改进可选，不作为方案前提）。
- **不引入新依赖**（边界 2）。
- **不动已封箱代码**除非必需（第 7 章）：`Osc1337Parser` 字节层**一行不改**。
- **内存态、不持久化**：session 不跨重启（ADR-008），标题状态同理。
- **性能底线**：标题解析在 PTY 热路径上，新增开销必须是 O(1) 常数级。

## 3. 核心设计：TitleSource（声明来源分级）+ TitleResolver（纯函数裁决）

### 3.1 模型

把「一个可变字段 + 一堆写入者」换成 **「多个带来源标签的插槽 + 一个纯函数裁决器」**。

```
                  ┌─────────────── 写入侧（带来源标签）───────────────┐
  renameSession ──┤ TitleSource.user        (优先级 40) 永久锁         │
  onPiName ───────┤ TitleSource.agent       (优先级 30) bridge 声明     │
  handleOscTitle ─┤ TitleSource.program     (优先级 20) 前台程序 OSC    │
       (同一通道) └ TitleSource.shell       (优先级 10) shell 自身/子进程│
  createSession ──┤ TitleSource.default     (优先级  0) 模板/shell 推断 │
                  └──────────────────────────┬─────────────────────────┘
                                             ↓
                        TitleState { [source]: value | null }
                                             ↓
                              resolveTitle(state)  ← 纯函数
                                             ↓
                              info.displayName（派生值，只读）
```

**关键点：`displayName` 从「被写的状态」变成「被算出的派生值」。**
写入者不再互相覆盖，而是各自更新自己的插槽；谁显示由 `resolveTitle` 一处决定。

### 3.2 类型（`src/shared/types.ts` / 新文件 `src/main/title-resolver.ts`）

```typescript
/**
 * 标题声明来源，按权威性排序。数值即优先级，高者胜。
 * 与 ADR-030 的 TerminalStateGetter 分层同构：来源分级，非平级覆盖。
 */
export const TitleSource = {
  /** 模板名 / shell 推断名（pickDisplayName），永远存在的地板值 */
  default: 0,
  /** shell 自身及其子进程的 OSC 0（PowerShell 启动名、cmd exe 路径、MINGW PS1） */
  shell: 10,
  /** 前台程序的 OSC 0（pi / vim / claude / make），有 program 就压住 shell */
  program: 20,
  /** agent bridge 明确声明（onPiName），比裸 OSC 更可信 */
  agent: 30,
  /** 用户手动命名，永久最高 */
  user: 40,
} as const;
export type TitleSourceKind = keyof typeof TitleSource;

/** 每个来源一个插槽；null = 该来源尚未发声 */
export type TitleState = Record<TitleSourceKind, string | null>;

/** 纯函数：取优先级最高的非空插槽。default 永不为 null，故必有返回值。 */
export function resolveTitle(state: TitleState): string;
```

`ManagedSession` 增加一个字段（替代 `manuallyRenamed` 布尔）：

```typescript
interface ManagedSession {
  // ...
  /**
   * 标题各来源的声明值。displayName = resolveTitle(titleState) 的派生结果。
   * manuallyRenamed 语义 = titleState.user !== null（保持 M1-C / STM-3 行为）。
   */
  titleState: TitleState;
}
```

### 3.3 谁来判定 program vs shell —— 唯一的真问题

OSC 0 是单一字节通道，pi 和 powershell 子进程用的是同一个序列。分类必须在 Marina 端完成。
按可靠性从高到低，**分层判定，先命中者胜**：

**第 1 层：OSC 133 前台状态（可靠，零猜测）**
Shell 集成协议 OSC 133 标记 prompt 生命周期：`133;A` prompt 开始、`133;C` 命令开始执行、
`133;D` 命令结束。语义直接给出「现在是 shell 在 prompt，还是有前台程序在跑」：

- 收到 `133;C` 后 → 前台有程序在跑 → 期间的 OSC 0 归 `program`
- 收到 `133;D` / `133;A` 后 → 回到 shell prompt → 期间的 OSC 0 归 `shell`

Marina 已有 `src/shell-hooks/` 注入机制（现在注入 OSC 1337 报 cwd），**同一个 hook 顺带发
OSC 133 即可**，成本极低。`Osc1337Parser` 增加识别 `133` 前缀（与 `1337` 的判定互不干扰：
先比 `1337;` 再比 `133;`，长前缀优先）。

**第 2 层：shell 自声明名单（兜底，覆盖无 hook 的 shell）**
shell hook 未注入 / 远程 SSH / 用户自定义 shell 时没有 OSC 133。此时用一个**极小的精确匹配
名单**把「已知的 shell 自我介绍」归到 `shell` 槽：

```
"Windows PowerShell", "Administrator: Windows PowerShell",
"命令提示符", "Command Prompt", "cmd", "cmd.exe",
+ 现有 looksLikeShellStartupGarbage 的 5 条正则（裸路径 / MINGW / 裸 exe）
```

注意语义变化：**这些标题不再被「丢弃」，而是被「归档到 shell 槽」**。
纯 shell session（没有 program 声明）时它们照常显示，只是永远压不过 pi 的 program 声明。
这同时**修掉一个现存缺陷**：今天 TIT-1 把裸路径直接丢弃，纯 shell session 就永远看不到
任何 shell 自报标题；分层后它至少能落到 shell 槽。

**第 3 层：默认归 program**
两层都没命中 → 归 `program`。这是安全的默认：陌生 CLI 工具的标题应当能显示，
而它只会与其他 program 竞争，抢不走 user / agent 槽。

### 3.4 生命周期：program 槽何时清空

program 槽必须能释放，否则 pi 退出后标题永远卡在 `pi - ...`。清空时机：

| 事件 | 动作 | 理由 |
|---|---|---|
| OSC 133 `D`（命令结束） | `program = null` | 前台程序退出，回归 shell 名（**最准**） |
| `onPiName(null)` / agent unbind | `agent = null` | 与 ADR-030 的 unbindAgent 对称 |
| PTY exit | 全部保留 | exited session 保留最后标题（现状行为，用户可辨认） |
| `clearManualRename` (STM-3) | `user = null` | 现状语义不变：交回自动标题 |

无 OSC 133 的 session：program 槽不主动清空（等价于今天的行为，不回归）。

## 4. 深度分析：为什么是这个形状

按 `codebase-design` 的词汇评估。

### 4.1 深度（Depth）

`TitleResolver` 的**接口**是两件事：`resolveTitle(state)` 和 `TitleSource` 枚举。
**实现**吸收了：优先级裁决、shell 名单匹配、OSC 133 前台跟踪、program 释放时机、
`manuallyRenamed` 兼容语义。

调用侧的收益（Leverage）——四个写入点从「各自判断能不能覆盖」变成「只声明自己是谁」：

```typescript
// 现在（每个写入点自己做权限判断，散落的 guard）
private handleOscTitle(managed, rawTitle) {
  if (managed.manuallyRenamed) return;              // guard 1
  const cleaned = sanitizeTitle(rawTitle);
  if (!cleaned) return;                             // guard 2
  if (looksLikeShellStartupGarbage(cleaned)) return; // guard 3（猜内容）
  if (cleaned === managed.info.displayName) return;
  managed.info.displayName = cleaned;
  this.emitStateChanged(managed, { displayName: cleaned });
}

// 之后（声明来源，裁决交给 resolver）
private handleOscTitle(managed, rawTitle) {
  const cleaned = sanitizeTitle(rawTitle);
  if (!cleaned) return;
  this.declareTitle(managed, classifyOscTitle(managed, cleaned), cleaned);
}

/** 唯一的 displayName 写入点 */
private declareTitle(managed, source: TitleSourceKind, value: string | null) {
  managed.titleState[source] = value;
  const next = resolveTitle(managed.titleState);
  if (next === managed.info.displayName) return;    // 去重只剩这一处
  managed.info.displayName = next;
  this.emitStateChanged(managed, { displayName: next });
}
```

`declareTitle` 成为 **`displayName` 的唯一写入点**（今天有 4 处写 + 3 处散落 guard）。
这就是 Locality：改标题策略只改 resolver，4 个调用点不动。

### 4.2 Seam 放在哪

Seam 在 **`resolveTitle` 纯函数 + `classifyOscTitle` 纯函数**，不在 SessionManager 方法上。
理由：这两个是**无副作用的裁决逻辑**，可以脱离 PTY / session / Electron 直接单测：

```typescript
// 测试不需要 FakePty、不需要 SessionManager
expect(resolveTitle({ default: 'PowerShell', shell: 'Windows PowerShell',
                      program: 'pi - 架构设计 - marina', agent: null, user: null }))
  .toBe('pi - 架构设计 - marina');   // ← 本 bug 的回归测试，一行
```

「接口即测试面」：这个 bug 的回归测试变成一次纯函数断言，不需要跑 Electron、不需要造字节流。
对照今天：要测同样的场景得起 FakePty、按顺序灌两段 OSC 字节。

**不做的 seam**：不给 TitleSource 做 adapter / 策略类。原则是
「一个 adapter 是假想的 seam，两个才是真的」——这里跨来源变化的只有*一个数值优先级*，
用枚举足够；引入 `TitleSourceStrategy` 接口是过度抽象。

### 4.3 与 ADR-030 的一致性（关键的架构自洽）

| ADR-030（state） | 本方案（title） |
|---|---|
| agent 信号 = 权威主源 | `user` / `agent` / `program` 高优先级源 |
| 字节流启发式 = fallback | `shell` / `default` 低优先级源 |
| 绑 agent 时字节流**完全旁路** | 有 program 时 shell 声明**不影响显示**（但仍归档） |
| `unbindAgent` 后恢复 fallback | program 槽清空后自动回落 shell / default |
| 抽象为 `TerminalStateGetter`（拉取模型） | 抽象为 `resolveTitle`（派生模型） |

同构但**不共用抽象**：state 用「拉取式 getter」因为它要响应 onByte/onWorking 事件流；
title 是「多槽派生」因为它没有事件流、只有值。强行统一成一个 `SessionFieldResolver<T>`
会得到一个既不像 getter 也不像 resolver 的中间物 —— 这是我明确拒绝的方案（见 §6.3）。

### 4.4 删除测试（The deletion test）

假设删掉 `TitleResolver`，复杂度会不会消失？不会 —— 它会重新散回四个写入点：
每个点都要重新问「我能不能覆盖现在的值」，`manuallyRenamed` 布尔会重新长出
`programEstablished`、`shellTitleSeen` 等第二第三个布尔（这正是当前代码演化的轨迹）。
所以这个模块在挣它的钱。

### 5.2 测试

纯函数层（新增，不需要 Electron）：
- `resolveTitle` 优先级矩阵：5 源 × 空/非空组合的关键路径
- **本 bug 的回归**：program=pi 标题 + shell=`Windows PowerShell` → 显示 pi 标题
- `classifyOscTitle`：OSC 133 在/不在、shell 名单命中/未命中、未知工具默认 program
- TIT-1 的 36 个 `looksLikeShellStartupGarbage` case **原样保留**，断言改为
  「归到 shell 槽」而非「被丢弃」

集成层（FakePty，扩展现有 `describe('SessionManager — OSC 0/1/2 标题')`）：
- pi 标题落地 → 子进程发 `Windows PowerShell` → **displayName 不变**（核心断言）
- OSC 133 `D` 后 → program 释放 → 回落 shell 名
- `manuallyRenamed` / STM-3 现有 4 个集成 case 全部保持绿

`scripts/smoke-interactive.mjs` 按 TIT-1 文档「防御性改进」建议补一条 displayName 断言。

### 5.3 性能

`resolveTitle` 是 5 个字段的常数比较，只在收到标题事件时跑（不在字节热路径每 chunk 跑）。
OSC 133 识别是 parser 里一次 `Buffer.equals` 前缀比较。均满足 §10 底线，无需缓存。

## 6. 被拒绝的方案（连同理由）

### 6.1 扩充 `looksLikeShellStartupGarbage` 名单（我上一轮给出的「主修复」）

加一条「`Windows PowerShell` 也算垃圾」。
**拒绝**：这是第四次给同一个猜内容的正则打补丁，TIT-1 已证明这条路走不通
（新 shell / 新语言 / 管理员前缀 / 中文系统会源源不断产生新变体）。
它治的是这一个字符串，不是「无法区分发声者」这个病。
（名单本身在新架构里仍然存在，但降级为**第 2 层兜底分类器**，不再是唯一防线 —— 从
「判断真伪」变成「判断归属」，误判的代价从「标题消失」降为「优先级偏低」。）

### 6.2 只加一个 `titleEstablished` 布尔（我上一轮给出的方案 1）

「收到首个合法 program 标题后，shell 名单不再覆盖」。
**拒绝**：这是把 `manuallyRenamed` 的模式再复制一遍 —— 每加一个来源就加一个布尔，
N 个来源要 2^N 的隐式组合，且「谁能覆盖谁」仍散落在 if 里。ADR-030 已经否决过这条路
（「ad hoc 协调，没有分层」）。一个 5 值枚举 + 纯函数比 3 个布尔更小也更清楚。

### 6.3 统一抽象 `SessionFieldResolver<T>`（把 state / cwd / title 三个字段合并）

看起来最「架构」：三个字段都是多源竞争，抽一个泛型 resolver。
**拒绝**：三者的时间模型根本不同 —— state 是事件流拉取（需要 onByte/onWorking 回调）、
cwd 是单源 + latch（不需要优先级）、title 是多槽派生（不需要事件）。
合并后的接口要同时暴露 getter 回调、latch 和优先级，对每个字段都有多余部分：
**大接口 + 薄实现 = 浅模块**，正好是要避免的形状。三个字段共享的是*设计原则*
（来源分级 + 兜底恢复），不是*代码*。原则靠 ADR 和文档传递，不靠泛型。

### 6.4 让 pi 更频繁地重发标题（改 pi 侧）

pi 在每个 agent turn / 工具执行后重发 `updateTerminalTitle()`。
**拒绝为主方案**：（a）Marina 不能依赖外部包的修复来保证自家 UI 正确；
（b）任何非 pi 的前台程序（vim / claude / 用户脚本）都有同样问题，治不了通用情况；
（c）本质是用「更高频的覆盖」赢竞态，仍是 last-writer-wins，抢不过恰好后到的子进程。
**可作为 pi 侧的独立改进上游反馈**，与本方案正交。

### 6.5 要求用户装 Marina 的 pi bridge 扩展

让 `onPiName` 通道生效。
**拒绝**：（a）把架构缺陷转成用户配置负担；（b）即使装了，`agent` 槽也只在 pi 主动改名时
更新，中途被 shell 抢标题的窗口依然存在（因为今天没有优先级，OSC 后到仍然赢）。
分层之后 bridge 变成**锦上添花**（agent 槽 30 > program 槽 20），而非必需 —— 这正是
好架构的标志：可选增强，不是前提。
