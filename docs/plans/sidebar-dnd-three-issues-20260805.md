## 问题 2：拖一个组想同级，结果被嵌入了（交互缺陷，可修）

### 你遇到的现象

你拖一个组（比如 `#2`），想让它和 `game` **同级**（都是 `marina` 的直接子组）。但提示线落在了 `game` 的子组区域（缩进更深），释放后 `#2` 变成了 `game` 的子组。

### 根因（一级一级讲）

1. **渲染结构**：一个组（比如 `game`）展开后，DOM 顺序是：
   ```
   [game 标题]          ← 标题行
   [#11 子组标题]       ← game 的子组列表区
   [#1  子组标题]       ← game 的子组列表区
   [p2 路径]            ← game 的路径列表区
   ```
   `game` 的**子组列表紧贴在 `game` 标题正下方**。

2. **你想"放到 game 的同级（后面）"时**，最自然的指针位置是 `game` 标题下方那一块——但那一块**恰恰是 `game` 的子组列表**，在视觉和数据上都属于 `game` 内部。

3. **当前命中逻辑**：指针落在 `game` 的子组列表区域时，无论 x 靠左还是靠右，都会被解析成"`game` 的子项"（嵌入 `game`），而**不是**"`game` 的同级后置"。原因是这块区域里能命中的行（#11、#1 标题，或空白兜底）全都属于 `game` 的子组容器。

4. **唯一能触发"同级后置"的窄区域**：指针**精确落在 `game` 标题栏那一行像素的下半 + x 靠左**。这个区域太窄、且视觉上和你想要的"放到 game 后面"不对应，所以几乎不可能稳定命中。

**结论**：这是真实的交互缺陷，不是你操作问题。**根因是"展开的组，其子组列表区域"和"该组之后的同级位置"在视觉上完全重叠，但当前模型只能把前者解析成嵌入。**

### 修复方案（成本：中改，单函数）

**方案 A1（推荐）：组列表尾部空白 = 同级后置启发式**
当指针落在某组的**子组列表空白区**（不在任何子组标题上）**且 x 靠左**（缩进等于该组父级），解析为"该组的同级后置"，而不是"嵌入该组"。
- 改动集中在 `resolveDropFromPoint` 的 container-tail 兜底分支（`Sidebar.tsx:1808-1841`）。
- 风险：改变了"空白=容器内末尾"的心智，但实际更符合直觉（空白靠左=出去、靠右=进去）。

**方案 A2**：扩大 group-head 的可命中区域为"标题 + 子组列表尾部带"。风险是可能和子组标题行冲突。

**待裁决**：是否采用方案 A1（子组列表空白 + x 靠左 = 同级后置）？这是我推荐的方向，贴合现有"y 选行 x 定层"模型。

## 问题 3：把路径放在两个子组中间（数据模型限制，需大决策）

### 你遇到的现象

你想把路径 `p2` 放在 `组1` 和 `组2` 之间，上级是 `game`。但发现拖动时 `p2` 只能放在路径堆里（所有子组之后），**插不进两个子组之间**。

### 根因（这是设计约束，不是 bug）

1. **数据模型**：在 `bookmarks.json` 里：
   - **路径**是全局扁平数组 `paths[]`，每条路径靠 `groupId` 指向所属组，路径的"组内序号"靠数组顺序。
   - **子组**存在组的 `subgroups[]` 数组里。
   - **两者是两个完全独立的有序集**——没有一个"统一的孩子序列"来表达"组1 → p2 → 组2"这种交错。

2. **渲染必然结果**：一个组的 DOM 永远是"先渲染所有子组（`subgroups` 容器），再渲染所有路径（`paths` 容器）"。所以路径在视觉上**永远排在所有子组之后**，不可能插在两个子组之间。

3. **这不是 bug，是当前数据模型的固有约束**。要让路径能插在两个子组之间，必须把"路径和子组"合并成一个统一有序的 children 列表。

### 两个产品方向，请你选

**方向 1：保持"子组在上、路径在下"的分区（不改数据模型）**

- 概念：**子组 = 容器/归类**（像文件夹），**路径 = 具体收藏**（像文件）。一个组内，归类在上、收藏在下，泾渭分明。
- 代价：路径不能和子组交错排列。
- 好处：零改动，概念清晰，与 `bookmarks.json` 现有 schema（v3）一致。
- 如果选这个，我会在交互上**更清楚地表达这个分区**（比如子组区和路径区之间加一条极淡的分隔线，或子组区有"分组"小标头），让你一看就懂"路径只能在这下面排"。

**方向 2：统一 children 有序列表，路径与子组完全混合排序（大改）**

- 概念：一个组的所有孩子（不管是子组还是路径）是一个**统一的有序列表**，任意交错。
- 代价（**大改**）：
  - 数据模型：`GroupNode` 从 `{id,name,subgroups}` 改为 `{id,name,children:[{kind:'group'|'path',id}]}` 统一列表。
  - 持久化：`bookmarks.json` schema 从 v3 升 v4，写迁移逻辑（v3 的子组在前、路径在后合并成 children）。
  - 后端：`path-manager.ts` 的 `reorderBookmarks`（核心排序逻辑）重写。
  - 拖拽层：`bookmark-dnd-layout.ts` 全量重构（placement / containerId / move 函数）。
  - 渲染层：`Sidebar.tsx` 的 GroupBlock 重构为单一有序容器。
  - 测试：迁移 + 排序全量重测。
- 风险：v0.3.3 已定稿 v3 schema，在收尾阶段做 schema 迁移有回归风险；工作量大（估 1-2 天）。

### 我的推荐

**方向 1（保持分区）**，理由：
- "容器在上、叶子在下"是**业界常见的树形 UI 约定**（VSCode 资源管理器：文件夹在上、文件在下；很多 IDE 同理）。用户通常能接受。
- v0.3.3 已在收尾，不值得为这个引入 schema 迁移的回归风险。
- 真正的需求大概率是"这个路径属于 game 组、排第几"，而不是"视觉上必须插在两个组中间"——分区能满足前者。

**待裁决**：方向 1（分区，我推荐）还是方向 2（混合排序，大改）？
