# 侧栏核心交互重设计：用户模型、推导与待裁决项

> 状态：**推荐方案 A 第一版已实施，等待用户手感验证**  
> 日期：2026-08-04  
> 触发原因：用户明确否定当前交付质量。`26c5491` 的“横向 24px 投影层级”已从正式路径删除。

## 0. 背景与已定结论

用户指出的不是几处视觉瑕疵，而是交互模型错误：

1. 分组右键与 `⋯` 打开完全相同的菜单，入口重复；只保留右键。
2. 分组菜单没有“向此组添加文件夹/路径”，用户必须先添加到未分组，再二次移动。
3. 分组拖拽不是真实容器落点，而是用“起始深度 + 横向像素”推导层级；用户不能直接控制目标父级。
4. session 拖拽只有释放后的排序结果，没有真实插槽和实时让位，手感同样不是所见即所得。
5. SSH 段没有 profile 时只提示“去设置”，创建连接被迫中断当前任务。
6. 不能只修用户逐条点出的地方；需要审计相邻入口是否也有重复、缺主任务、隐藏手势、设置绕路和反馈滞后。

以下是已经确定、无需再次裁决的结论：

- 删除分组行的 `⋯`；分组管理只通过右键菜单进入。
- 删除 `requestedDepth`、`deltaX / 24`、ancestor projection 这套层级推导。
- 拖拽结果必须直接来自一个真实的 `{targetContainerId, targetIndex}`。
- 拖动过程中必须先产生与最终结果相同的预览树；释放只是提交预览，不能释放后再猜。
- SSH 新建连接必须在 SSH 当前任务内完成，设置页只负责批量管理。

## 1. 我之前为什么会做错

### 1.1 我按数据结构设计了界面，没有按用户任务设计

代码里有 `groups / subgroupOrder / childOrder / sshProfiles`，我就围绕这些名词提供“新建子组、重排、添加 profile”。

但用户面对的任务不是“修改 subgroupOrder”，而是：

- “把这个文件夹放进 A。”
- “把 C 从 B 里拿出来，放到 A 里。”
- “现在连接一台新机器。”

**设计后果：**每个入口和结果都必须使用用户能看见的对象——组、文件夹、终端、连接——而不能要求用户理解内部树结构。

### 1.2 我把“算法能算出结果”误当成“用户能控制结果”

当前代码：

- `Sidebar.tsx:1466-1490`：`activeDepth + round(deltaX / 24)` 得到 requestedDepth；
- `bookmark-dnd-layout.ts:215+`：再根据命中行祖先链投影 parent/index。

算法对给定输入是确定的，但用户不知道：

- 现在已经横移了 18px 还是 25px；
- 起始层级会怎样影响结果；
- 命中 B 时算法最终取 B、A 还是根作为父级。

**设计后果：**确定性必须建立在用户能直接指向的目标上，而不是建立在内部公式上。

### 1.3 我把“提供反馈”误当成“修正映射”

增加“根级 / 与 B 同级”的标签，只能告诉用户算法猜了什么，不能让用户直接选择目标。错误映射加上清楚标签，仍然是错误映射。

**设计后果：**先让输入和结果一一对应，再谈动画、标签和颜色。

### 1.4 我只测了数据正确，没有测控制感

此前验证关注：

- 最终 DOM 缩进对不对；
- bookmarks.json 顺序对不对；
- console 有没有报错。

这些只能证明“系统完成了一次移动”，不能证明：

- 用户是否能第一次就放对；
- 同一屏幕位置是否总产生同一结果；
- 用户移动过程中能否预测释放结果；
- 放错后是否容易恢复。

**设计后果：**新的验收必须包含命中率、目标预测、取消、自动展开、边缘滚动和错误恢复，不再只断言最终 JSON。

## 2. 这里的用户是谁、当时注意力在哪里

Marina 用户主要在终端工作。侧栏不是独立的信息管理器，而是终端任务的空间索引。

典型状态：

- 用户刚执行完命令，注意力仍在主终端；
- 需要快速整理一个路径、终端或连接；
- 不愿切换设置页、记住中间状态、完成配置后再找回来；
- 侧栏密度高，鼠标目标小，频繁使用时手部精度成本会累积。

因此“舒服”的定义不是“动画好看”，而是：

1. **少记忆：**不用记内部层级规则或刚才在哪个页面。
2. **少导航：**任务在当前对象附近开始和结束。
3. **大目标：**高频拖放不要求命中 10px 缩进沟槽。
4. **可预测：**释放前看到的树，就是释放后的树。
5. **可取消：**Esc 或拖出合法区域，原数据完全不变。
6. **不撒谎：**界面移动不能暗示底层事实也改变了（例如把正在运行的 shell 伪装成属于另一个 cwd）。

## 3. 统一交互原则

### 原则 A：主任务可见，低频管理右键

- 分类 `+`：执行当前分类的主任务。
  - 当前电脑收藏：添加文件夹；
  - 当前电脑临时：打开文件夹并创建终端；
  - SSH：连接已有机器或新建连接。
- 分组右键：针对这个组的内容和结构操作。
- 删除重复 `⋯`。同一个菜单有两个入口会制造两个疑问：
  1. 两个入口是否有差别？
  2. 哪一个才是推荐入口？

用户已明确选择右键，视觉上应只保留组名、折叠状态和内容，不再放管理 icon。

### 原则 B：对象菜单必须包含“向对象加入内容”

右键 A，菜单首先应该回答“我能对 A 做什么”。最高频任务不是重命名 A，而是把内容放进 A。

菜单顺序建议：

1. **添加文件夹到「A」…**
2. **新建子组**
3. 分隔线
4. **重命名**
5. **解散分组**（危险色；明确“内容提升，不删除数据”）

为什么舒服：

- 菜单标题是 A，动作结果也落在 A；对象—动作映射直接。
- 添加后一次完成，不再“先未分组 → 再移动到 A”。
- 高频内容动作在上，低频结构动作居中，危险动作在底部。

为什么当前设计不舒服：

- 菜单只允许创建子组、改名、解散，像是在管理一个空壳；
- 用户明明右键 A，却无法把文件夹加到 A；
- 二次移动增加一次选择器、一次定位和一次拖拽，还可能放错。

### 原则 C：拖拽目标必须是实际容器和实际插槽

数据模型中本来就存在这些真实列表：

- 根组列表：`root.groups`
- A 的直接子组列表：`A.subgroups`
- B 的直接子组列表：`B.subgroups`
- 未分组路径列表：`ungrouped.paths`
- 每个组的路径列表：`group.childOrder`
- 每个 path 的 session 列表：`path.sessionIds`

新的拖拽系统直接注册这些容器。每个容器有 `0..N` 个真实 insertion slot。

唯一合法结果：

```text
{ draggedId, targetContainerId, targetIndex }
```

禁止再出现：

```text
{ activeDepth, horizontalDelta, requestedDepth, overAncestor }
```

### 原则 D：预览树是真值，释放只提交

拖动过程状态：

```text
idle
  → picked(sourceId)
  → preview(targetContainerId, targetIndex)
  → commit(previewLayout)
  → settled(main broadcast)
```

- picked：源位置保留一个空壳，避免列表突然跳动。
- preview：把拖动项真正插入内存中的目标列表；周围项实时让位。
- commit：直接提交当前 previewLayout。
- Esc / 无合法 slot：丢弃 preview，恢复 sourceLayout。

为什么舒服：用户释放前已看见最终结构，不需要“试一下看会去哪”。

### 原则 E：设置负责管理，当前界面负责任务

- “我要连接一台机器”是即时任务，应在 SSH 段完成。
- “批量修改、删除、检查所有连接”是管理任务，才属于设置。

把即时任务扔进设置，会让用户：

1. 离开当前侧栏；
2. 寻找远程分类；
3. 填表保存；
4. 记住原任务；
5. 返回侧栏；
6. 再点一次连接。

这是典型的上下文切换和工作记忆负担。

## 4. 分组拖拽：用户应该怎么操作

示例：

```text
A
  B
    C
```

### 4.1 拖动开始

用户在 C 的整行按下并移动超过普通点击阈值：

- C 生成跟随鼠标的 DragOverlay；
- 原位置留下与 C 等高的 source placeholder；
- 只有合法的 group container/slot 出现，C 自身和后代不生成目标。

为什么不是移动原 DOM：原 DOM 同时承担布局和拖影会导致 rect 变化、跳动和嵌套碰撞；overlay 只负责“手里拿着什么”，preview tree 负责“放下会怎样”。

### 4.2 放到 A 内，与 B 同级

用户把 C 拖到 **A 的子组列表中，B 后面的真实插槽**。

进入插槽时：

```text
A
  B
  [ C 的等高占位 ]
```

B 和占位左缘完全一致。释放后，数据直接写：

```text
targetContainerId = A.subgroups
targetIndex = indexAfter(B)
```

### 4.3 放到根级，与 A 同级

用户把 C 拖到 **根组列表中，A 后面的真实插槽**。

进入插槽时：

```text
A
  B
[ C 的等高占位 ]
```

占位与 A 左缘一致。释放后直接写：

```text
targetContainerId = root.groups
targetIndex = indexAfter(A)
```

### 4.4 放进 B

用户把 C 拖到 B 行本身。B 行是一个大目标，语义为“放入 B”：

- B 展开时：在 `B.subgroups` 尾部显示 C 的占位；
- B 折叠时：悬停约 450ms 自动展开，再显示占位；
- 立即划过不展开，避免列表乱跳。

### 4.5 根/父级插槽重叠时怎么办

这是树拖拽真正困难的地方，也是不能再“靠算法猜”的地方。

删除 C 后，`B 后（A 内）` 与 `A 后（根级）` 可能处于同一个纵向边界。两个目标不能叠在同一像素区域。

**推荐方案：拖动时展开“插槽阶梯”。**在该边界临时形成两个有实际高度的目标：

```text
  ┌ 放在「A」内 · 与「B」同级 ┐
┌ 放在根级 · 与「A」同级       ┐
```

- 每个目标至少一行高，不要求命中 12px 缩进沟槽；
- 左缘等于最终层级；
- 鼠标进入其中一个后，该项膨胀成完整的 C 占位，另一项保持紧凑；
- 这是两个真实 DOM droppable slot，不是文案覆盖层。

为什么舒服：目标不仅被说明，而且真的占据不同空间；用户指向哪个，数据就落到哪个。

为什么不用横向拖动阈值：

- 横向位移是“手势历史”，不是屏幕上的对象；
- 同一当前位置可能因起始点不同得到不同层级；
- 多层树要求累计精确位移，手抖和缩放都会影响结果；
- 用户无法在释放前证明当前越过了哪条阈值。

为什么不只用窄缩进沟槽：

- 12px 目标违反高频鼠标操作的目标尺寸要求；
- 多级沟槽并排时误差一格就是完全不同的父级；
- 侧栏还可能缩窄、缩放或滚动。

## 5. session 拖拽：用户应该怎么操作

当前代码 `Sidebar.tsx:1757-1776` 只在 dragEnd 后 arrayMove，然后发 `SESSION_REORDER`。拖动过程中没有目标插槽真值。

推荐：

- session 行使用 DragOverlay；源处保留空壳。
- 同一 path 的 session 列表生成真实 `0..N` 插槽。
- 鼠标进入插槽，完整 session 占位立即移动；其他 session 实时让位。
- 释放提交当前 `orderedSessionIds`；Esc 恢复。
- 指针离开本 path 的合法列表，placeholder 消失并显示禁止状态。

为什么默认不允许把 session 拖到另一个 path：

- shell 进程的 cwd/启动目录没有因为 UI 拖放而改变；
- 若把 session 显示到另一个路径下，界面会对进程归属撒谎；
- 当前后端 `SESSION_REORDER` 也只接受同一 `pathId` 的顺序。

如果产品未来定义“path 只是用户自定义容器，不代表 session 目录”，才能支持跨 path；这会改变领域模型，不能作为拖拽手感修复顺便加入。

## 6. 路径拖拽也必须使用相同模型

不能只修 group，留下 path 的 `closestCenter` 猜测。

- 未分组路径列表是真实容器；
- 每个 group 的路径列表是真实容器；
- 组行可作为“追加到该组”大目标；
- 路径插槽显示完整 path 行占位；
- 释放提交 previewLayout；
- local/SSH 隐藏 segment 的 path 仍必须保留在全量 payload 中。

对象类型必须隔离：

- group 只能进入 group container；
- path 只能进入 path container；
- session 只能进入当前 path 的 session container。

这样不会发生“鼠标看起来落在组行，算法却碰到了组下面的 path/session wrapper”。

## 7. SSH：用户应该怎么创建和连接

### 7.1 点击 SSH 段的 `+`

无论当前有 0、1、N 个 profile，都打开同一个“连接 SSH”面板，而不是：

- 0 个：toast 叫用户去设置；
- 1 个：不询问就直接连接；
- 多个：才显示菜单。

建议内容：

```text
连接 SSH

最近/已有连接
  ● prod        alice@example.com
  ● dev         bob@10.0.0.8

  + 新建 SSH 连接
```

为什么单 profile 也不应静默直连：`+` 的语义是“发起一个连接任务”，用户可能正是要新建第二台机器。自动连接把“数量”偷偷变成了交互模式。

### 7.2 新建 SSH 连接表单

第一屏只显示完成连接必需的信息：

- 主机
- 用户名
- 认证方式（SSH agent/默认配置、密钥、密码）

自动/默认：

- 名称默认生成 `user@host`，用户可改；
- 端口默认 22，放进“更多选项”；
- 默认目录 `~`；
- ProxyJump、默认目录等放进“更多选项”。

主按钮：**保存并连接**。

提交链路已有能力：

```text
SSH_PROFILE_ADD
  → 返回新 profile.id
  → makeSshPathId(profile.id, '~')
  → SESSION_CREATE
```

不需要先去设置，也不需要新增连接后端。

为什么舒服：

- 用户点击“连接”，流程结束时真的得到终端，而不是只得到一条配置；
- 常用字段少，低频高级字段不阻塞；
- 校验错误显示在对应字段附近，表单内容不丢；
- 创建成功后 profile 自动持久化，下次出现在已有连接列表。

### 7.3 设置页的职责

设置页保留：

- 编辑/删除全部 profile；
- 批量检查密钥、agent、known_hosts；
- 修改高级选项。

设置页不再是首次连接的必经路径。

## 8. “向此组添加文件夹”的完整后端语义

当前 `PathManager.addBookmark` 没有 groupId，新收藏总先进未分组，再依赖 reorder。

正确语义应为原子操作：

```text
BOOKMARK_ADD { path, groupId? }
```

main 在同一次事务中：

1. 校验 path；
2. 校验 groupId 存在；
3. 检查重复收藏；
4. 创建 bookmark 并直接设置 groupId；
5. 持久化；
6. 广播一次最终 pathTree。

为什么不能“先 add，再 reorder”：

- UI 会短暂闪到未分组；
- 第二步失败会留下半完成状态；
- reorder 要提交全量 layout，增加无关数据冲突面；
- 用户执行的是一个动作，后端也应是一个原子命令。

选择器分流：

- 客户端本机：系统 folder picker；
- 远程 Marina backend：现有 `BackendDirectoryPicker`；
- SSH：当前没有远端目录浏览能力，不能用文本框破坏“路径不可手输”原则。需要单独提供 SSH 目录浏览数据源，或在这项能力完成前明确禁用并说明原因，不能假装三者等价。

## 9. 举一反三后的相邻问题

### 9.1 收藏分类标题也有右键 + `⋯` 重复

`Sidebar.tsx:365-400` 两个入口都只有“新建分组”。

建议同样删除分类 `⋯`：

- `+`：主任务（添加文件夹 / 连接 SSH）；
- 分类右键：新建顶层分组。

### 9.2 SSH 的 0/1/N profile 三种行为不一致

数量不应改变入口模型。统一连接面板，避免：

- 0 个是死路；
- 1 个意外直连；
- N 个才允许选择/新建。

### 9.3 Settings 的 Remote 分类对新用户可能不可见

当前代码甚至需要在“高级”里放 `enableRemote` 兜底。首次 SSH 连接就地完成后，设置分类应负责管理，不应靠已有 profile 决定自己是否存在。

### 9.4 SSH 远端收藏仍用文本路径

这与“路径只能选择/拖拽”的产品原则冲突。不能在新表单里继续复制这个输入框；需要单独设计远端目录浏览。

### 9.5 错误不能只用 toast

拖拽或表单失败时：

- 拖拽：恢复 sourceLayout，并在源位置附近给一次原因；
- SSH 表单：错误绑定字段，保留输入；
- toast 只用于跨对象、无法绑定到具体控件的错误。

### 9.6 折叠和拖拽不能争抢点击

- 普通单击：折叠/展开；
- 移动超过阈值：进入拖拽，不能再触发 click；
- 右键：菜单；
- 拖动悬停折叠组：延迟自动展开。

必须真实指针测试三者不会串扰。

## 10. 被否决的方案

1. **横向每 N px 改一级**：目标由手势历史推导，不是实际容器。
2. **目标行上半/下半分别 sibling/nest**：不可发现；无法表达多级祖先。
3. **只增加文字标签**：反馈无法修复错误输入映射。
4. **只用缩进沟槽选层级**：高频目标太窄，多级误触代价高。
5. **松手后再计算并播放动画**：释放前不可预测。
6. **先添加未分组，再自动 reorder**：非原子，可能闪烁和半失败。
7. **SSH 无 profile 时跳设置**：中断任务，增加工作记忆。
8. **有一个 profile 就自动连接**：把 profile 数量暗中变成交互模式。
9. **在 SSH 表单继续让用户手输远端目录**：违反项目路径输入红线。

## 11. 为什么推荐方案会更舒服

| 用户感受 | 产生它的设计机制 |
|---|---|

| “手不用特别稳” | slot 至少一行高；重叠边界展开为插槽阶梯 |

## 12. 原型计划（先验证手感，不直接写生产代码）

在真实 Marina 侧栏密度下做 3 个 throwaway 变体：

### A — 插槽阶梯（推荐）

- 普通 gap 是真实插槽；
- 多级容器共享边界时，展开为多行目标；
- hover 后显示完整等高 placeholder。

要验证：目标是否足够大、列表展开是否过度扰动。

### B — 容器块

- 拖动时每个 group 的 child container 显示边界；
- 组内、组外由不同实际块决定；
- placeholder 在块内实时移动。

要验证：深层树是否出现太多边框和视觉噪音。

### C — 固定层级目标栏

- 拖动时侧栏底部出现“根级 / A / B”大目标；
- 指向目标后，树中显示最终 placeholder。

要验证：虽然容易命中，但是否因目标和实际位置分离而不够直接。

三者都禁止使用 `deltaX → depth`。原型必须用 CDP 真实鼠标事件，不只调用函数。

## 13. 需要一次性裁决的问题

### 问题 1：session 是否允许跨 path 移动？

**背景事实：**当前 `SESSION_REORDER` 只排序同一 path 的 session；session 的实际 cwd 不会因 UI 拖放改变。

**待裁决点：**拖到另一个 path 是改变“显示归属”，还是应该禁止？

**推荐：**禁止跨 path，只做同列表所见即所得排序。否则 UI 会暗示 shell 属于一个它并未进入的目录。

### 问题 2：拖到 group 行本身是否统一表示“放入此组末尾”？

**背景事实：**行是最大的稳定鼠标目标；精确排序由行间 slot 负责。

**待裁决点：**group 行是“进入组”，还是还要区分前/后？

**推荐：**行本身只表示“进入组末尾”；前/后只能通过真实间隙，避免一块区域多重语义。

### 问题 3：多级边界采用哪种可操作原型？

**背景事实：**父/祖先容器在末尾可能共享同一纵向边界，必须产生不同物理目标。

**选项：**A 插槽阶梯 / B 容器块 / C 固定目标栏。

**推荐：**先做 A、B、C 三版，当前倾向 A；不凭文档直接写生产代码。

### 问题 4：SSH 新建表单的主按钮是什么？

**背景事实：**用户从侧栏 `+` 进入，意图是连接，不只是存 profile。ADD 已返回 profile.id，可立即 SESSION_CREATE。

**选项：**“保存” / “保存并连接” / “连接但不保存”。

**推荐：****保存并连接**为主按钮；设置页继续提供单纯保存/编辑。

### 问题 5：有一个 SSH profile 时，`+` 是否还直接连接？

**背景事实：**当前一个 profile 会直接连接，导致没有入口创建第二个。

**推荐：**不直接连接；0/1/N 都打开统一连接面板，已有连接一击可选，“新建 SSH 连接”始终可见。

### 问题 6：分类标题的 `⋯` 是否与分组一起删除？

**背景事实：**收藏分类右键和 `⋯` 同样重复，菜单都只有“新建分组”。

**推荐：**一起删除。`+` 保留主任务；右键保留结构管理。

### 问题 7：SSH 组菜单“添加文件夹”是否要求本轮同时做远端目录浏览？

**背景事实：**local/Marina backend 有 picker；SSH 当前只有文本路径，没有浏览 IPC，而文本输入违反产品红线。

**推荐：**如果要求三种 backend 体验一致，则本轮必须把 SSH 目录浏览列为正式子任务；在它完成前不放一个会退化为手输路径的假入口。

## 14. 实施前验收标准

### 菜单

- 分组行没有 `⋯`。
- 分类标题没有重复 `⋯`（若问题 6 通过）。
- 右键组 A 首项是“添加文件夹到 A…”。
- 选择成功后路径只出现一次，直接位于 A；无未分组闪烁。

### group/path 拖拽

- 不存在 `requestedDepth`、`deltaX / N`。
- 每个 preview 都能打印明确 `{targetContainerId,targetIndex}`。
- A→B→C：C 能分别放到 `B.subgroups`、`A.subgroups`、`root.groups`，三个目标是不同真实 DOM hit area。
- 拖动中其他行实时让位；释放前截图与释放后截图结构相同。
- Esc、拖出、后端拒绝都恢复源布局。
- 折叠组悬停延迟展开；快速划过不展开。
- 边缘拖动自动滚动。
- 自身/后代完全不注册为合法 slot。

### session 拖拽

- 同一 path 的每个插槽可命中；实时占位。
- 离开当前 path 不显示合法落点（若问题 1 按推荐裁决）。
- 释放前顺序预览 = 持久化后顺序。

### SSH

- 0/1/N profile 的 `+` 都进入同一个连接面板。
- “新建 SSH 连接”始终可见。
- 新建成功后无需关闭面板/进入设置，直接出现 SSH terminal。
- 后端校验错误留在表单内，字段值不丢。
- 设置页仍能编辑/删除刚创建的 profile。

### 验证方式

- shared/main 单测锁住 container/index 语义和原子 add(groupId)。
- 真实 Electron + CDP `Input.dispatchMouseEvent` 覆盖拖起、移动、占位、释放、Esc。
- 录屏/连续截图检查真实让位和折叠展开，不用最终 DOM 代替过程验证。
- renderer console/exception 0 error。
