# 远程窗口错误态架构修复（设计 + 决策对齐）

> 这是一份 grilling 文档：根因已查清（事实部分），剩余的是架构方向的决策点。
> 请逐条裁决，每条我都给了推荐 + 理由。
> 文档自包含——开发者可能在另一个 session 打开它。

---

## 背景与已定结论（已查清的事实，不是决策）

### 用户报告的两个 bug

- **Bug 1**：协议版本不匹配时，弹出的错误窗口**没有 title bar**（没有最小化/最大化/关闭那一栏）。用户说之前修过类似的「报错丢 title」bug，但协议版本这条路径又复发了。
- **Bug 2**：远程窗口还没连上时，窗口用的是**默认主题**。按设计（`docs/plans/远程窗口外观继承本机.md`），远程窗口的前端外观应**继承本机客户端设置**，所以应该是用户自己设的主题。

### 关键事实：所有窗口都是 `frame: false`（自绘标题栏）

`src/main/window-manager.ts:192` 唯一的窗口工厂 `createWindow()` 里：

```ts
frame: false,   // 系统 OS 标题栏整条拿掉
```

**没有任何 `titleBarStyle` / `titleBarOverlay`。** 标题栏 100% 由 renderer 的 `<WindowChrome>` 组件自绘（`src/renderer/components/WindowChrome.tsx`）。

**推论（这是 Bug 1 的机制基础）**：在 `frame: false` 的窗口里，**任何不渲染 `<WindowChrome>` 的可见状态 = 无标题栏**。这不是某一处忘了配置，而是「自绘标题栏 + 错误态选了不画标题栏的组件」共同导致的。

### App.tsx 里有 4 条握手/错误分支，标题栏覆盖不一致

`src/renderer/App.tsx` 里的窗口可见状态共 4 种：

| 分支 | 位置 | 远程窗口是否有标题栏 | 主题来源 |
|---|---|---|---|
| `pending`（握手中） | App.tsx:131 | ❌ `FullPagePlaceholder`（瞬时） | 无 |
| **`mismatch`（协议版本不匹配）** | **App.tsx:135-143** | **❌ `FullPagePlaceholder`（没查 `?backend=`）** | **无 → 默认** |
| `handshake error`（连不上 daemon） | App.tsx:146-174 | ✅ `RemoteConnectionErrorScreen`（查了 `?backend=`） | fallback `rose-pine` |
| `sync.error`（snapshot 拉取失败） | App.tsx:337-354 | ✅ `RemoteConnectionErrorScreen`（查了 `?backend=`） | fallback `rose-pine` |

`mismatch` 分支是四条里**唯一**没做「远程窗口 → 渲染带标题栏错误页」分流的。这就是 Bug 1。

### 为什么会「修了又复发」（架构根因）

git log 显示 2026-07-07 同一天连续三个 commit 修同一类 bug：

1. `b501a24` 引入 `RemoteConnectionErrorScreen`（带标题栏错误页）
2. `409e619` 给错误页补 `data-theme` + Provider 树
3. `00fd171` 真正生效——根因是 `handshake error` 分支走了无标题栏的 `FullPagePlaceholder`，补了 `?backend=` 分流 + `AppStateProvider`

**这三个 commit 都只修了 `handshake error` 分支。`mismatch` 分支（同一个函数里的另一个 `if`）从未被覆盖。**

架构上为什么必然复发，有三个根因：

1. **没有统一的「错误/握手态外壳」**：`FullPagePlaceholder`（精简、无标题栏）和 `RemoteConnectionErrorScreen`（完整、带标题栏）两个组件并存，每条分支**自己决定**用哪个、**自己决定**要不要查 `?backend=`、**自己决定**要不要挂 `AppStateProvider`。每新增/遗漏一条分支就复发一次。
2. **`?backend=`（判断是不是远程窗口）的判定逻辑在 App.tsx 里重复了 3 次**（150 行、340 行附近），没提取，新增分支时容易漏写。
3. **本机外观获取与「连接成功路径」死耦合**：见下面 Bug 2。

### Bug 2 的根因：外观获取嵌在连接成功路径里，错误路径拿不到

「远程窗口外观继承本机」**已经实现**（commit `372de2b` + `1f98677` + `01f550c`）：

- 本机外观通过 local-control 命令 `SETTINGS_GET_APPEARANCE` 拉取（`src/shared/protocol.ts:174`）。
- 这个命令是 **local-control 域**：远程窗口调用它时走**客户端本地 IPC**（`ipcRenderer`），**不经过远程 WS 连接**。证据：`RemoteConnectionErrorScreen` 里的 `WindowChrome` 已经通过另一条 local-control 命令 `REMOTE_PROFILE_LIST` 拉到了 profile 名（`WindowChrome.tsx:106-122`），**即使远程连不上也能工作**。

**但**：本机外观的覆盖逻辑写在 `useIpcSync()` 里（`store.tsx:1066-1091`），而 `useIpcSync` 只在握手 OK 后的 `ConnectedShell`（App.tsx:178）挂载。

**所以**：所有错误路径（`mismatch` / `handshake error` / `sync.error`）都不调 `useIpcSync` → store.settings 保持空对象（`store.tsx:765`）→ `state.settings.appearance?.theme` 为 `undefined` → `RemoteConnectionErrorScreen` 里 `const currentTheme = state.settings.appearance?.theme ?? 'rose-pine'`（App.tsx:497）**永远 fallback 到默认 `rose-pine`**。

**讽刺点**：远程连不上时，拉本机外观的通道 `SETTINGS_GET_APPEARANCE` 本来完全可用（它走本地），只是错误页**根本没去调它**。这是 Bug 2。

---

## 设计目标

1. **根治复发**：让「frame:false 窗口的可见状态没标题栏」这件事在结构上**不可能再发生**，而不是靠每条分支记得画标题栏。
2. **根治 Bug 2**：让本机外观的获取与「连接是否成功」**解耦**，错误态也能拿到本机主题。
3. 不顺手重构无关代码（遵守「已通过代码不许重构」红线）；只动错误/握手态这条链路。

---

## 决策点 1：统一「frameless 窗口外壳」组件（架构根治的核心）

### 上下文 / 推理过程

当前问题本质：`frame: false` 的窗口里，组件树**必须**包含 `<WindowChrome>` 才有标题栏，但这个约束**没有被编码进结构**，全靠每个分支的作者自觉。`FullPagePlaceholder` 这个组件本身就是一个「陷阱」——它在 frame:false 窗口里是个残缺组件（永远无标题栏），但名字看起来像个通用占位组件，于是 `mismatch` 分支很自然地用了它。

### 名词定义

- **frameless 窗口外壳（FramelessShell）**：一个包裹组件，职责是「在 frame:false 窗口里保证标题栏 + 应用本机外观 + 挂起码 Provider 树」。它内部渲染 `<WindowChrome>` + `<div data-theme data-window-style>{children}</div>`。

### 待裁决点

是否引入一个统一的 `<FramelessShell>`（或叫别的名字），把 `RemoteConnectionErrorScreen` 现有的「外壳职责」（WindowChrome + data-theme + Provider 树）上提，让所有 4 条分支（pending / mismatch / handshake-error / sync.error）都变成 `<FramelessShell><具体内容/></FramelessShell>` 结构？

### 我的推荐：是，引入统一外壳

理由：
- 把「frame:false 窗口的可见状态必有标题栏」从**口头约定**变成**结构强制**。以后任何人新增错误分支，只要走 `<FramelessShell>`，标题栏就不可能丢。
- `RemoteConnectionErrorScreen` 瘦身成「只负责错误卡片内容」（标题、诊断清单、复制、重试/关窗按钮），外壳职责不再和它耦合。
- 这是「修架构 bug」，不是「为重构而重构」，符合 YOLO 边界。

## 决策点 2：错误/握手态怎么拿到本机外观（解耦 Bug 2）

### 上下文 / 推理过程

现状：本机外观获取嵌在 `useIpcSync` 的 snapshot 流程里（`store.tsx:1066-1091`），错误路径不走这条流程，所以拿不到。

技术前提（已验证）：`SETTINGS_GET_APPEARANCE` 是 local-control 命令，远程窗口调用走客户端本地 IPC，**远程连不上时依然可用**（与 `WindowChrome` 里已工作的 `REMOTE_PROFILE_LIST` 同机制）。

### 名词定义

- **local-control 命令**：协议里声明为 `LOCAL_CONTROL_COMMANDS_SET`（`protocol.ts:440`）的命令。远程窗口调用时走客户端本地 IPC，不经远程 WS。

### 备选方案

- **方案 A：独立 hook `useLocalAppearance()`**
  一个 hook，App 挂载时（握手之前）就并发拉本机外观（`SETTINGS_GET_APPEARANCE`）+ 订阅 `SETTINGS_LOCAL_APPEARANCE_CHANGED`，返回 `{ theme, windowStyle, ... }`，fallback 默认值。`<FramelessShell>` 从它读主题。错误态天然拿到本机主题。
- **方案 B：根层 Context Provider `<LocalAppearanceProvider>`**
  在 App 最顶层（握手之前）包一个 Provider，内部拉本机外观并注入 context。`<FramelessShell>` 和正常路径都从 context 读。
- **方案 C（不推荐）**：每个错误组件自己 invoke `SETTINGS_GET_APPEARANCE`。重复、易漏，等于把现在的「每条分支自己决定」问题换了个地方重演。

### 待裁决点

选 A（hook）还是 B（Provider）？以及：是否**同时简化** `useIpcSync` 里那段重复的本机外观拉取（让它也改从 hook/Provider 读，避免「连接成功路径拉一次、根层又拉一次」双写）？

### 我的推荐：方案 B（Provider）+ 简化 useIpcSync 那段

理由：
- 本机外观是「无论连接成功与否、无论本地还是远程窗口，都需要」的**客户端基础外观**，应该在 App 最顶层尽早拉，天然早于任何握手结果。Provider 语义最贴切。
- Provider 一次拉取、全局共享；`useIpcSync` 里那段「远程窗口再拉一次本机外观覆盖 snapshot」就**重复**了，应改成「从 Provider 读 + 订阅 Provider 的事件」，消除双写（snapshot 里的 daemon 外观直接被 Provider 的本机外观覆盖，逻辑不变，只是数据源收敛）。
- A（hook）的问题：如果 `ConnectedShell` 和 `<FramelessShell>` 各自用 hook，会各自拉一次（除非 hook 内部做单例缓存），不如 Provider 干净。
- 关于「不许重构已通过代码」红线：这段是当前 checkpoint 内代码，且是 bug 修复必需（消除双写数据源不一致风险），不是为重构而重构。如开发者认为风险高，可保留 useIpcSync 那段不动、仅让 Provider 做错误态兜底（双写但互不冲突，本机外观是幂等的）。

> **依赖**：决策点 2 的选择会影响决策点 1 的 `<FramelessShell>` 内部实现（它从哪读主题）。先定 2，再定 1 的实现细节。

## 决策点 3：本地窗口（非远程）的错误态要不要也带标题栏？

### 上下文 / 推理过程

本地窗口也会走到 `mismatch`（main/renderer 协议不一致）和 `handshake error`（`window.api` 不存在）。这些路径**当前也走 `FullPagePlaceholder`（无标题栏）**。本地窗口同样是 `frame: false`，所以本地出错时一样无标题栏——只是用户这次报告的是远程窗口，本地这条没被注意。

### 待裁决点

统一外壳是否覆盖本地窗口的错误态（让本地出错也有标题栏）？

### 我的推荐：是，统一覆盖

理由：
- `frame: false` 对本地/远程都生效，「无标题栏 = 像卡死」的体验对本地用户一样糟。
- 统一后只剩一套外壳，架构最简单，也杜绝「本地出错无标题栏」这个潜在 bug 被未来某天报告。
- 本地出错时 Provider 拉本机外观走本地 IPC（就是它自己的 settingsManager），照样能拿到本机主题；极端情况（settingsManager 本身坏了）fallback `rose-pine`，可接受。

## 决策点 4：`pending`（握手中）状态要不要标题栏？

### 上下文 / 推理过程

当前 `pending`（App.tsx:131）用 `FullPagePlaceholder`，无标题栏。理论上是瞬时的，但慢网络下用户会盯着一个无标题栏的窗口几秒。

### 待裁决点

`pending` 也走统一外壳吗？

### 我的推荐：是

理由：消除「握手中无标题栏 → 连上了突然有标题栏」的闪烁；统一后零额外成本（外壳本来就包了）。`pending` 内容就是个「正在连接…」的卡片，套进 `<FramelessShell>` 即可。

---

## 决策点 5：`FullPagePlaceholder` 这个组件去留

### 上下文 / 推理过程

如果决策点 1/3/4 都通过，`FullPagePlaceholder` 在 App.tsx 里就没有调用方了（4 条分支全改走外壳）。

### 待裁决点

删除 `FullPagePlaceholder`，还是保留作为「极简、无标题栏、纯展示」的底层组件？

### 我的推荐：删除

理由：在 frame:false 项目里，一个「无标题栏的可视组件」本身就是个**陷阱**（诱使新代码误用导致复发）。删掉它，让「无标题栏」这个状态在代码里根本不可表达，是最强的防复发。如果将来真需要极简展示，套进 `<FramelessShell>` 即可。

## 实施方案概要（决策通过后这么做）

> 顺序依赖决策点 2 的选择。下面按「方案 B（Provider）」写。

1. **新增 `<LocalAppearanceProvider>`**（`src/renderer/`）：App 最顶层挂载，握手前就拉 `SETTINGS_GET_APPEARANCE` + 订阅 `SETTINGS_LOCAL_APPEARANCE_CHANGED`，注入 `{ theme, windowStyle, ... }` context，fallback 默认值。本地/远程窗口都适用（都拿「本机客户端」外观，符合「外观归属客户端」原则）。
2. **新增 `<FramelessShell>`**：内部渲染 Provider 树 + `<WindowChrome>` + `<div data-theme data-window-style>{children}</div>`，主题/windowStyle 从 `useLocalAppearance()` 读。
3. **改造 4 条分支**（App.tsx）：
   - `pending` / `mismatch` / `handshake error` / `sync.error` 全部变成 `<FramelessShell><内容卡片/></FramelessShell>`。
   - `mismatch` 内容卡片：协议版本不匹配的说明 + 关窗按钮（远程/本地通用）。
   - 远程窗口的连接错误卡片保留 `RemoteConnectionErrorScreen` 的诊断/复制/重试逻辑（只剥掉它的外壳职责）。
4. **简化 `useIpcSync`**（可选，看决策点 2 的最终结论）：那段「远程窗口拉本机外观覆盖 snapshot」改为从 Provider 读，消除双写。
5. **提取 `?backend=` 判定**：App 根层算一次 `const isRemoteWindow = !!backendId`，传给需要的分支，消除 3 处重复。
6. **删除 `FullPagePlaceholder`**（决策点 5 通过则删）。
7. **测试**：
   - `mismatch`（远程 + 本地各一种）：有标题栏、可关窗、主题 = 本机主题。
   - `handshake error`（远程断开 daemon）：有标题栏、主题 = 本机主题、诊断/复制/重试可用。
   - `sync.error`：同上。
   - `pending`：有标题栏，无闪烁。
   - 主题切换实时性：错误态下在本机切换主题，错误页主题跟着变（验证 Provider 的 `LOCAL_APPEARANCE_CHANGED` 订阅）。
   - 本地窗口正常启动：外观行为零回归（Provider 拿到的就是本机自己的外观）。
8. **更新文档**：本设计文档标注裁决结果；如涉及 ADR 则补 ADR；`远程窗口外观继承本机.md` 补「错误态也继承」的说明。
