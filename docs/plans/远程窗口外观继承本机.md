## 0. 一句话结论(先看这个)

**远程窗口的外观(appearance)应当归"当前客户端机器"所有,而非远程 daemon 机器。**
实现上复刻项目里已有的成熟先例 `remoteBackendProfiles`(snapshot 里某字段属于本地域
→ 用 local-control 命令重新拉取覆盖),风险低、模式一致。

> 不需要改 windowDefaults(窗口尺寸/位置):它已经天然用本机(见 §1.3)。

## 1. 背景与已定结论(把前面查清的事实复述一遍,让本文档自包含)

### 1.1 远程后端架构(每窗口后端模型)

Marina 支持把 Main Process 部署到另一台机器(`--headless --daemon`),本地 UI 作为
client 通过 WebSocket 连过去。每个窗口创建时**绑定一个 backend**:

- `backend = null`(本地窗口):命令走本地 Electron IPC。
- `backend = <profileId>`(远程窗口):命令走 WS → 远程 daemon。

判定依据:`src/preload/index.ts:100-103` 从窗口 URL `?backend=<profileId>` 解析。
窗口创建时定死,生命周期内不变(切后端 = 开新窗口)。

### 1.2 命令路由域(核心机制,这是本功能的支点)

`src/shared/protocol.ts:341-412` 定义了两个域:

- **`local-control`**(本地控制面):永远走**客户端机器**的 Electron IPC,**即使远程窗口也走本地**。
  管的是"当前客户端机器的本地资源":BrowserWindow 生命周期、剪贴板、本机的远程 profile 凭据、
  本机是否对外提供 daemon 服务、workspace(ADR-024)等。
- **`backend-data`**(后端业务数据,默认):本地窗口走本地 IPC,远程窗口走 WS → daemon。
  session/path/template/settings 等业务状态属于这里。

**关键设计**:新增命令只要在 `LOCAL_CONTROL_COMMANDS_SET`(protocol.ts:369-405)声明,
preload 通过 `getCommandRouting()` 自动路由,**不用改 preload**。注释原话:"这避免了
'新增本地控制命令忘记加到 preload' 的隐式契约 bug"。

### 1.3 外观设置当前从哪来(问题根源)

外观属于 `Settings.appearance`(`src/shared/types.ts:361-415`),包括:

| 字段 | 作用 |
|---|---|
| `theme` | 主题(18 个内置主题 id) |
| `windowStyle` | 窗口装饰风格 `windows` / `macos` |
| `language` | UI 语言 `system` / `zh-CN` / `en-US` |
| `terminalFontFamily` / `terminalFallbackFont` | 终端字体 + 回退字体 |
| `terminalFontSize` / `terminalLineHeight` | 终端字号 / 行高 |
| `uiFontFamily` / `uiZoom` | UI 字体 / UI 缩放 |
| `macOSTrafficLightHoverSymbols` | macOS 红绿灯 hover 符号 |
| `hideTopTabBar` | 隐藏顶部 TabBar |

`cmd:settings:get` / `cmd:app:get-snapshot` / `cmd:settings:update` / `evt:settings:changed`
**全部属于 `backend-data` 域**。所以:

- 远程窗口的 snapshot(`APP_GET_SNAPSHOT`)→ 走 WS → **返回 daemon 机器的 settings.json**。
- `state.settings` 在 `src/renderer/store.tsx:287-305` 的 `snapshot/load` 里被**整体赋值**为
  `s.settings`(即 daemon 的);`settings/changed`(store.tsx:555-556)也是整体替换。
- 外观消费点(`App.tsx:230-234`、`TerminalView.tsx`、`MainPane.tsx`、`WindowChrome.tsx`、
  `LanguageProvider.tsx`)全部读 `state.settings.appearance` → **远程窗口显示的是 daemon 机器的外观**。

→ 这就是用户看到的问题:**远程窗口用了远程机器的主题/字体/语言,而不是本机的。**

### 1.4 已有的完美先例:`remoteBackendProfiles`

项目**已经解决过一模一样的问题**,模式可以直接复刻:

> "remoteBackendProfiles 是'本客户端如何连接其他电脑'的本地控制面数据,不能信任远程
> snapshot 里的同名字段:远程窗口的 snapshot 来自 daemon,那里保存的是 daemon 自己的
> profile 列表。REMOTE_PROFILE_LIST 被声明为 local-control,远程窗口调用时也会走客户端
> 本地 IPC。"
> —— `src/renderer/store.tsx:1004-1010`

代码(store.tsx:1011-1023):snapshot 拿到后,再用 local-control 的 `REMOTE_PROFILE_LIST`
重新拉本机的,覆盖掉 snapshot 里 daemon 的值;失败时保留 snapshot 值兜底。

**本功能把 `appearance` 当成第二个"属于客户端本地"的字段,走同一套套路即可。**

### 1.5 已天然继承本机的部分(不用改)

- **`windowDefaults`(窗口尺寸/位置)**:`src/main/index.ts:311-333` 的 `setCreateOptionsProvider`
  用的是**本地** `settingsManager.get().windowDefaults`(window-manager 跑在本地 main 进程,
  BrowserWindow 是本地创建的)。→ 远程窗口的初始尺寸/位置**已经是本机的**,无需改动。
  *(注:关窗时 `onBeforeClose` 也写本地 settingsManager,行为一致。)*

## 2. 核心方案(复刻 remoteBackendProfiles 模式)

把 `appearance` 纳入"客户端本地控制面":新增 local-control 命令让 renderer 能拉/改本机
appearance,新增 local-control 事件让本机改了外观能实时推到远程窗口;store 层在远程窗口
用本机 appearance 覆盖 daemon 的。

### 2.1 数据流(目标态)

```
远程窗口启动
 ├─ APP_GET_SNAPSHOT (backend-data, 走 WS)  → 拿到 daemon 的 settings/session/path...
 ├─ SETTINGS_GET_APPEARANCE (local-control, 走本地 IPC) → 拿到【本机】appearance
 └─ store: snapshot.settings.appearance ← 本机 appearance  (其余字段仍用 daemon 的)

运行中:本机改外观
 └─ 本地 main settingsManager → 广播 evt:settings:local-appearance-changed (local-control)
     → 远程窗口 store 更新 appearance (其余 settings 字段不动)

运行中:daemon 改业务设置(非外观)
 └─ evt:settings:changed (backend-data, 走 WS) → store 只应用【非 appearance】字段

远程窗口里用户改外观(设置页)
 └─ SETTINGS_UPDATE_APPEARANCE (local-control, 走本地 IPC) → 写【本机】settings.json
     → 同机其他窗口也会收到本机广播,一致更新
```

### 2.2 新增的协议通道(全部声明为 local-control)

在 `src/shared/protocol.ts` 的 `COMMAND_CHANNELS` / `EVENT_CHANNELS` 新增,并加入
`LOCAL_CONTROL_COMMANDS_SET` / preload `LOCAL_CONTROL_EVENTS`:

| 通道 | 类型 | 域 | payload / 返回 |
|---|---|---|---|
| `cmd:settings:get-appearance` | 命令 | local-control | 入参空;返回 `{ appearance: Settings['appearance'] }` |
| `cmd:settings:update-appearance` | 命令 | local-control | 入参 `Partial<Settings['appearance']>`;无返回(写入本机 settingsManager) |
| `evt:settings:local-appearance-changed` | 事件 | local-control | `{ appearance: Settings['appearance'] }` |

> 命名可斟酌(也可叫 `get-local-appearance` / `update-local-appearance`)。"appearance"
> 比 "local-settings" 更窄、更准确——这个通道**只管外观**,不触碰 shell/behavior/advanced。

### 2.3 main 侧 handler(`src/main/ipc.ts` + `settingsManager`)

- `get-appearance`:返回 `settingsManager.get().appearance`。
- `update-appearance`:`settingsManager.update({ appearance: { ...current, ...partial } })`。
  → 复用现有 `settingsManager`,**自动触发写盘 + `settingsChanged` 广播**(见下)。
- 广播桥接:本地 `settingsManager` 已在 `evt:settings:changed`(backend-data)广播给本地窗口。
  新增:再广播一份 `evt:settings:local-appearance-changed`(local-control)给**所有窗口**
  (本地窗口也会收,但本地窗口直接用 `settings/changed` 即可,见 §2.4)。

### 2.4 store 层改造(`src/renderer/store.tsx`,改动主战场)

判断"是否远程窗口":`window.api.backendProfileId != null`(preload 已暴露)。

- **snapshot/load 后**(store.tsx:1016 附近):
  远程窗口时,并发拉 `SETTINGS_GET_APPEARANCE`,成功则用本机 appearance 覆盖
  `snapshot.settings.appearance` 再 dispatch;失败兜底保留 daemon 值(对齐 remoteBackendProfiles)。
- **`settings/changed` 事件**(backend-data,store.tsx:555-556):
  远程窗口收到时**只合并非 appearance 字段**,保留本机 appearance(`{ ...state.settings, ...daemonSettings, appearance: state.settings.appearance }`)。
- **`local-appearance-changed` 事件**(local-control,新增订阅):
  远程窗口收到时替换 appearance: `{ ...state.settings, appearance: payload.appearance }`。
  本地窗口忽略此事件(它已有 `settings/changed`,避免双重更新)。

### 2.5 设置页(`src/renderer/components/SettingsView.tsx`)

- `SettingsView.tsx:158` 当前 `SETTINGS_UPDATE` 是 backend-data,远程窗口会写 daemon。
- 改造:appearance 分类的提交,远程窗口改走 `SETTINGS_UPDATE_APPEARANCE`(local-control,写本机)。
  其余分类(shell/behavior/advanced 等)保持 `SETTINGS_UPDATE` 不变(归后端)。

## 3. 决策结论(已裁决)

> 开发者已确认:**§3 四项决策全部采用推荐方案**。以下固定为实现依据,不再变动。
> 各小节保留推理过程供实现时参考(各小节内的"推荐"即最终采用方案)。

### 问题 1:继承范围 —— appearance 全继承,还是只继承部分?

**上下文**:`appearance` 块有 11 个字段(见 §1.3 表)。用户原话是"外观方面的设置",
最自然理解是全部 appearance。但有两个边界字段值得单独确认:

- `language`(UI 语言):语义上偏"界面外观",但也有人认为"语言是内容不是外观"。
  我倾向**继承本机**——你坐在本机前,UI 该显示本机习惯的语言,而不是 daemon 机器的。
- `windowStyle`(windows/macos 装饰风格):这是**用户视觉偏好**,不是 OS 探测。
  用户可能在 macOS 上选了 windows 风格。我倾向**继承本机**,跟随用户在本机的偏好。

**不在继承范围的(归后端,确定不动)**:`shell`、`behavior`、`systemIntegration`、
`advanced`(含 `terminalRenderer`)。理由:这些是业务/行为设置,影响 session/shell,
属于后端机器的运行环境。

**待裁决点**:appearance 全块继承,含 language 和 windowStyle?

- ✅ **推荐:appearance 全块继承(11 个字段全要)**。理由:它们都是"客户端观感",
  语义一致;单独挑字段会增加心智负担和实现复杂度,收益为零。
- 备选:只继承 theme/字体/zoom,language/windowStyle 留给 daemon —— **不推荐**,割裂观感。

---

### 问题 2:实时性 —— 运行中本机改外观,是否实时同步到已打开的远程窗口?

**上下文**:方案 §2.1 里我设计了 `evt:settings:local-appearance-changed` 实时广播。
另一种选择是**只在开窗时继承一次**,之后本机改了外观,已开的远程窗口不跟(要重开才更新)。

**推理**:
- 实时同步需要新增一个 local-control 事件 + store 订阅,工作量略多。
- 但体验一致性是 Marina 的产品哲学之一(见软件定义书第 2 章)。本地窗口改主题是**所有本地
  窗口实时同步**的(store.tsx 的 `settings/changed`);远程窗口不跟会形成"同机两个窗口
  改主题不同步"的割裂感,用户会困惑。
- 实现成本可控:就是 §2.2 多一个事件通道 + §2.4 store 多一个订阅分支。

**待裁决点**:实时同步 vs 仅开窗时继承一次?

- ✅ **推荐:实时同步**(新增 local-control 事件)。理由:体验一致,割裂感是观感类 bug。
- 备选:仅开窗继承 —— **不推荐**,除非你想砍 MVP 范围(那也要显式接受割裂感)。

---

### 问题 3:远程窗口里【设置页】的外观项 —— 可改(写本机)还是只读?

**上下文**:`SettingsView.tsx:158` 当前用 `SETTINGS_UPDATE`(backend-data)提交。
如果外观继承本机,那么远程窗口里用户改外观应该写到哪?

三种选择:
- **A. 可改,写本机**(方案 §2.5):新增 `SETTINGS_UPDATE_APPEARANCE`(local-control),
  远程窗口设置页改外观 → 写本机 settings.json。本机其他窗口也跟着变。
- **B. 只读 + 提示**:远程窗口里外观项禁用/灰显,加一行提示"外观跟随本机设置,
  请在本地 Marina 窗口修改"。
- **C. 维持现状(写 daemon)**:外观显示用本机,但改了写 daemon —— **自相矛盾,排除**。

**推理**:
- A 保持设置页功能完整,用户在哪都能改外观,符合"设置页可用"的直觉。
- B 更"诚实"(外观归本机,远程窗口不该碰),但用户在远程窗口想改外观时要多跳一步,反人类。
- 我倾向 A:设置页是用户控制台,让它能改;写本机也符合"外观归本机"的归属。

**待裁决点**:A 还是 B?

- ✅ **推荐:A(可改,写本机)**。理由:设置页是用户控制台,保持可用;写本机与归属一致。
- 备选 B:如果你担心"远程窗口改了影响本机其他窗口"的副作用,可选 B。

---

### 问题 4(次要):回退兜底 —— 拉本机 appearance 失败时怎么办?

**上下文**:拉本机 appearance 的命令可能失败(本地 main 版本旧没注册新命令 / 协议不匹配)。
这和 `remoteBackendProfiles` 的兜底完全同构(store.tsx:1015-1022 的 try/catch 保留 snapshot 值)。

**待裁决点**:失败时回退 daemon appearance?

- ✅ **推荐:失败回退 daemon appearance**(对齐 remoteBackendProfiles 兜底模式)。
  理由:不阻塞 UI 启动;最坏情况退回当前行为(daemon 外观),不比现在差。
- 这是明显最佳实践,**如无异议默认采用**。

## 6. 风险与注意事项

- **不破坏本地窗口(零回归)**:所有远程分支都以 `backendProfileId != null` 守卫;
  本地窗口走原有路径。Step 3 的本地窗口忽略 `local-appearance-changed` 事件。
- **daemon 侧复用同一 installIpcLayer**:新 local-control 命令 daemon 也会注册 handler,
  但**远程窗口永远不会把这些命令发给 daemon**(preload 路由判定),daemon 的 handler
  只服务于"daemon 自己机器上的本地窗口"(如有)。需在测试确认不会误路由。
- **协议版本兼容**:旧 client 连新 daemon / 新 client 连旧 daemon 时,新通道可能不存在,
  靠 §3 问题 4 的兜底 + 握手版本检查兜住。
- **不碰 windowDefaults**:§1.3 已确认它天然用本机,**本次不要改**它的归属
  (改了反而引入"远程窗口尺寸异常"的回归风险)。
