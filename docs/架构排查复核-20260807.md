# Marina 代码架构排查复核

**日期**：2026-08-07  
**审计基线**：`feat/v0.3.3` / `b7294be`  
**最终复核 HEAD**：`feat/v0.3.3` / `b8db462`  
**性质**：只读诊断；除本报告外未修改产品代码

> 审计期间同一工作区并发进入了 3 个与本审计无关的提交（settings、command-panel、远程错误态）。本报告已在 `b8db462` 重新核对四项 High 结论并重跑全量验证；它们均未被这些提交触及。`b8db462` 已关闭审计基线上的“错误态拿不到本机外观”低严重度问题，见下文。

## 结论摘要

Marina 的核心状态机、持久化、后台调度和终端热路径总体质量较高；全量 typecheck、lint、1338 个测试均通过。真正应先修的不是“大文件多”，而是四个 seam（接缝）问题：

1. **远程功能 bug**：七个 `WORKSPACE_*` 命令被路由到客户端本地 Main，而不是当前远程 daemon。
2. **owner 契约缺口**：file-panel/gallery 的 Renderer IPC 没有 owner 校验，文件、Git、目录快照又被广播给全部 client。
3. **协议接口分散**：channel、类型、路由、授权、运行时校验不在同一份穷尽定义里；漏分类默认进入远程 backend。
4. **退出流程无 quiesce**：业务状态开始销毁/flush 后，IPC、WS、HTTP 仍可接受新工作。

建议先修这四项并补回归测试，再收敛 SessionManager、FilePanelService、Platform seam 和 renderer store。不要做“大文件即拆分”的大爆炸重构。

## High 1 — `WORKSPACE_*` 路由到错误进程

### 证据

- 远程连接的数据按产品规范归 daemon，appearance 是唯一客户端本地例外：`docs/软件定义书.md:2363-2368`。
- workspace/file-panel 的远程价值正是 workspace、agent 与 daemon 同机：`docs/软件定义书.md:2304-2309`。
- 七个 workspace 命令却被列为 `local-control`：`src/shared/protocol.ts:429-437`。
- preload 因此把它们发给客户端本地 IPC：`src/preload/index.ts:323-341`。
- handler 随后查询客户端本地 `SessionManager`：`src/main/ipc.ts:2756-2843`；远程 session 不在该 manager 中。
- renderer 的 workspace 快照恢复/写入依赖这些命令：`src/renderer/workspace-snapshot.ts:43-89,133-172`。

### 影响

远程窗口中的 workspace 快照读取通常返回 `null`，写入静默 no-op；scroll、运行结果和 bind 后恢复与远端真实 workspace 脱节。

### 最小修复

1. 从 `LOCAL_CONTROL_COMMANDS_SET` 移除七个 `WORKSPACE_*`，让它们走 `backend-data`。
2. 增加 routing 断言及 RemoteTransport ↔ RemoteDaemon 的 workspace read/write round-trip 测试。
3. 同批审查 `SYSTEM_OPEN_DATA_DIR`、`SYSTEM_OPEN_LOGS_DIR`、Explorer integration 等 OS/UI 命令在远程窗口中的归属。

**置信度：高。**

## High 2 — File-panel owner 能力边界缺失，事件路由违反协议

### 证据链

- 非 owner 只能看到 session 存在，不能直接显示其内容：`docs/软件定义书.md:230-235`。
- 协议明确 `evt:file-panel:updated` 仅推 owner：`docs/ipc-protocol.md:1884-1886`。
- 七个 file-panel/gallery handlers 没有传入或校验 `envelope.windowId`：`src/main/ipc.ts:2020-2110`。
- `FilePanelService` 只按 `sessionId/path` 操作；`openFile` 接受绝对路径，`readFile` 只检查路径是否已在面板列表：`src/main/file-panel-service.ts:381-454,523-563,920-954`。
- file-panel、Git、file-tree 快照广播给全部 `ClientRegistry` client：`src/main/ipc.ts:2562-2575,2619-2635`。
- file-panel payload 带绝对路径：`src/shared/types.ts:934-946`。
- `requestActivation=true` 会写入收到事件窗口自己的 `activePanels`：`src/renderer/store.tsx:467-500`。

### 判断

这是确认的产品/协议授权缺陷与**同账户数据外发**：非 owner client 会收到文件绝对路径、Git 变更和目录快照，并能主动读取/改动别的 session 的 file panel。

当前 daemon token 本身是同一用户的完整后端控制凭据，并非多租户权限，因此不应夸大为新的跨账户提权漏洞。未来若出现分级 token，严重度会立即升级。

### 最小修复

1. 只在 **Renderer IPC adapter** 增加统一 `requireSessionOwner(sessionId, clientId)`，覆盖 get/open/open-path/show/close/read/read-image/gallery。
2. 不要把该校验强塞进 FilePanelService 核心：终端内 HTTP agent 在 session orphan 时仍应 program-push 并更新 main 真值。
3. file-panel/Git/file-tree 有 owner 时 `sendEventTo(owner)`；orphan 时不推，状态保留在 main。
4. 新 owner mount/claim 后经现有 get/list/status 补拉。
5. 加双 client 测试：非 owner 命令拒绝、事件只到 owner、orphan 更新在接管后可补拉。
6. 同类审查 scrollback 与 command-panel 操作；它们也没有统一 requester policy。

### 长期 seam

使用 `CommandContext { clientId, transport }` 与声明式 authorization policy，例如 `ownerOf(payload.sessionId)`。FilePanelService 保持 transport-agnostic，由 Renderer client facade 与 HTTP agent facade 执行不同授权。

**置信度：高。**

## High 3 — 协议接口分散，路由边界 fail-open

### 当前事实

- 134 个 command channel 没有 `channel → payload/result/routing/authorization` 单一映射。
- preload 的 `invoke<P,R>(channel: string, ...)`、main 的 `registerHandle<P>(channel: string, ...)` 均由调用方手填泛型：`src/preload/index.ts:274-287`、`src/main/ipc.ts:393-429`。
- 路由只列 local-control；漏列命令默认 `backend-data`：`src/shared/protocol.ts:390-448`。High 1 已证明这会产生真实 bug。
- WS 只浅校验 frame，没有 payload schema；server 未设项目级 `maxPayload`：`src/main/transport-ws.ts:76-111,174-194`。
- 文档已采用 `clientId/ownerClientId/targetClientId`，wire schema 仍叫 `windowId/ownerWindowId`：`src/shared/protocol.ts:555-565`、`src/shared/types.ts:262-263`。
- `makeIpcError` 有 `details`，WS dispatcher 只保留 code/message；本地 Electron 又依赖自定义 Error 属性序列化：`src/main/ipc.ts:473-494,2720-2729`。

### 修复顺序

1. 先改为穷尽的 `Record<CommandChannel, CommandRoutingDomain>`；未知 channel 两端拒绝。
2. 加静态测试：每个 command 恰好注册一次、恰好分类一次。
3. WS 校验 channel 白名单、requestId 类型/长度、payload 存在性并设置 `maxPayload`；高风险命令先手写 validator，无需立即引入依赖。
4. 统一 local/WS 的结构化错误 envelope。
5. `windowId → clientId` 作为一次显式协议 major bump 完成。

长期建立 `CommandContractMap`，每项同时定义 payload、result、routing、authorization、validator，并派生 typed invoke/register/dispatcher。

**置信度：高。**

## High 4 — 退出流程没有 quiesce 阶段

- `before-quit` 先 shutdown session/scheduler，再异步 flush：`src/main/index.ts:429-463`。
- 期间未停止 RemoteDaemon、FilePanel HTTP，也未让 IPC/WS dispatcher 拒绝新命令。
- `index.ts` 被 `ipc.ts`、`tray.ts` 反向 import，只为退出标志，形成唯一 runtime import SCC：`src/main/index.ts:23-33`、`src/main/ipc.ts:236`、`src/main/tray.ts:43`。
- `getIsQuitting()` 是零消费者导出：`src/main/index.ts:74-82`。
- lifecycle 内嵌在 Electron entry，`index.ts` 又被 coverage 排除：`vitest.config.ts:58-64`。

### 影响与修复

退出窗口内仍可能创建 session、spawn command 或改 store，动作可能落在 shutdown/flush 之后。

最小顺序应为：原子进入 `quiescing` → transport gate 拒绝新工作 → 停 WS/HTTP ingress → 停任务与 session → flush。把 quit 状态抽到无副作用模块以消除 cycle；长期由 `AppLifecycleController` 管理 `running → quiescing → flushing → stopped`。

> 1 秒 flush 预算可以是防卡死权衡；确认问题是预算期间仍接受新工作。

**置信度：高。**

## Medium — 应收敛的 module seam

### 1. IPC 层承担业务生命周期编排

`wireEventBroadcasts` 在 session owner/exited/destroyed 时清 Git、file-tree、command、view lease、runner 和 file panel：`src/main/ipc.ts:2509-2558`。资源清理因此依赖 IPC 已安装。

**建议**：移入可测试的 `RuntimeLifecycleCoordinator`；IPC 只做事件序列化与定向。

### 2. SessionManager 的 interface 已跨域

`SessionManager` 有 57 个方法，其中 34 个 public。PTY、owner、输出聚合、headless scrollback、cwd 与状态转移是合理 cohesive core，应保留。

真正越界的是：

- workspace/Pi 编排：`src/main/session-manager.ts:688-709,1572-1902`；
- Git availability、prefetch、布局策略：`711-729,775-812,2574-2660`；
- 具体 `AIClient` 依赖：`2360-2439`；
- 构造器注入但未使用的 `WindowManager`：`748-756`。

**建议**：先抽 `SessionWorkspaceCoordinator` 与 `SessionPresentationPolicy`。AI 作为 `ActivityClassifier` 策略注入，最终状态转移仍留在 SessionManager。

### 3. FilePanelService 已成为通用 Agent HTTP gateway

`FilePanelService` 有 55 个方法、22 个 public、5 个 `attach*`、13 个 HTTP endpoint。文件列表/read/watch/size 限制是合理核心；HTTP/auth/body/routing 及 workspace/screenshot/command/Pi 回调是跨域 seam：`src/main/file-panel-service.ts:95-180,240-293,1193-1285`。

**建议**：抽 `AgentHttpGateway`；FilePanelService 只实现 panel interface。不要再把 cohesive 的 state/read/watch 机械拆碎。

### 4. Platform seam 漂移

平台层明文禁止核心代码直接判断平台：`src/main/platform/index.ts:1-16`，但 platform 外仍有约 15 个生产判断。重点是 `index.ts` 的 lifecycle/tray/cold-start（`415-427,750-848,921-927`）和 platform 外的 Windows Explorer 模块（`src/main/explorer-integration.ts:20-49,133-245`）。

**建议**：优先把 lifecycle、tray/startup-open、Explorer integration 放回 capability boundary。不要把所有能力堆成新的 God `PlatformAdapter`；按 lifecycle、file-manager integration、spawn/path semantics 分服务。纯 telemetry 的平台读取可保留。

## Low / 先测量再改

### 已关闭：错误态的 client-local appearance bootstrap

审计基线 `b7294be` 中，appearance 只在 backend snapshot 成功后补拉，握手失败页因此拿不到本机主题。并发提交 `b8db462` 已在 App 顶层、handshake 之前挂载 `LocalAppearanceProvider`：`src/renderer/App.tsx:41-48`、`src/renderer/components/LocalAppearanceProvider.tsx:53-87`。该问题不再列为开放发现。

`AppSnapshot` 仍混有 backend settings、client-local profiles 与 window state（`src/shared/types.ts:874-890`），长期可分离 `BackendSnapshot` 与 `ClientBootstrapState`，但成功路径已有覆盖逻辑，当前仅是边界清晰度债务。

### 单 Context 的 render fanout

Provider value 随每次 state 变化：`src/renderer/store.tsx:789-833`；`TerminalDeck` 和每个 parked `TerminalView` 都订阅完整 AppState：`src/renderer/components/TerminalDeck.tsx:34-56`、`TerminalView.tsx:667-710`。

这能确认“不必要 React render 的机制”，但 PTY 字节流不走 reducer，xterm effect 也未依赖整个 state，因此尚无性能底线违规实证。先用 React Profiler；再让 TerminalView 只订阅 appearance/behavior/simpleMode 和自身 session selector。只加 `React.memo` 不足以阻断 context 更新。

### Panel cache 清理契约漂移

`clearPanelUiState` 文档称 session destroy 时调用，生产代码无调用者；测试只直接调用。若 id 不复用，影响主要是运行期小量陈旧 Map，而不是立刻错误。补接 cleanup 或删除错误契约即可，不应列 P0。

## 明确不建议做的重构

1. **不要按 LOC 拆文件**：`index.ts` 天然是宽 composition root；SessionManager 的 PTY core 与 FilePanelService 的 file-state core 都是合理 deep module。
2. **不要给 Git/FileTree 轮询抽共用基类**：二者已共享 `BackgroundWorkScheduler`，但去重键和 HOT/WARM 策略不同；再抽基类会隐藏差异。
3. **不要因为两个 profile manager 相似就先造泛型 Repository**：在确认领域不变量真正相同前，这会制造浅抽象。
4. **不要先统一所有 renderer state**：owner/routing/lifecycle 是正确性问题；Context selector 是测量后的性能改进。
5. **不要把 local Error code 丢失写成已确认 P0**：这是高风险不一致，但仍需最小 Electron 主/渲染进程复现验证具体序列化行为。

## 建议实施顺序

### Phase 0：锁住契约（最小改动）

1. 修 `WORKSPACE_*` routing，并补远程 round-trip 测试。
2. 加 file-panel requester owner guard 与 owner-only 事件测试。
3. 将 routing 改为穷尽表；增加 command 注册/分类完整性测试。
4. 覆盖 scrollback、command-panel、file-panel、Git、file-tree 的统一能力矩阵。

### Phase 1：统一协议边界

1. 引入 `CommandContext` 与 authorization metadata。
2. typed `CommandContractMap`；统一 local/WS error envelope。
3. 补 WS runtime validation 与 payload 上限。
4. 规划 `clientId` 协议升级。

### Phase 2：生命周期深模块

1. `RuntimeLifecycleCoordinator` 接管 session 资源清理。
2. `AppLifecycleController` 接管 quiesce/shutdown/flush 顺序。
3. 消除 `index ↔ ipc/tray` cycle，并给 lifecycle 状态机加单测。

### Phase 3：只抽确认的跨域 seam

1. Session workspace/presentation policy。
2. Agent HTTP gateway。
3. platform capabilities。
4. Profiler 证实后再引入 renderer selectors。

## 最终判断

当前代码不是“整体架构失败”，而是产品从单机 Electron 演进到多窗口、远程 daemon、terminal-side agent 后，**旧的 window-centric transport interface 没有同步升级为 client capability interface**。最有效的修复主线是：

> **先把 routing + authorization + lifecycle 变成显式、穷尽、可测试的深模块，再沿已确认的跨域 seam 缩窄 SessionManager、IPC 和 FilePanelService。**

这比按文件大小拆分更安全，也更符合 Marina 的 Main 唯一真值、owner 独占内容、远程 daemon 数据归属和窗口平等原则。
