# Marina 打包发布流程

**最后更新**:2026-09-03
**适用版本**:0.3.3-dev.13 起(unpacked 默认清理);0.1.0-beta.10 起其余内容
**作者**:Liyue-Cheng + Claude Opus 4.7
**文档状态**:**当前唯一权威**(替代之前散落在 `docs/checkpoints/` / `AGENTS.md` 4.2 / `CHANGELOG.md` 里的零散描述)

> 历史背景:beta.9 之前每次发版都是作者手工跑一串命令,任何漏掉或顺序错都会带来回归。最直接的代价是 ISO-1(详见 `docs/issues/iso-1-cross-platform-build-pollution.md`)— 从 beta.5 到 beta.9 共 5 个安装包都夹带错平台 .node 二进制,没人系统校验过。本文档把整套流程钉死,让 release 从"作者本地经验"变成"任何人在任何机器上能复现"。

---

## 0. 一句话:怎么发版?

```bash
# 单平台
npm run release:win               # Windows 包(nsis + portable)
npm run release:linux             # Linux 包(.deb + .rpm + .AppImage)

# 全平台一次发完
npm run release:all

# 升版号 + 发版一气呵成
npm run release:all -- --bump=prerelease

# 不知道会跑什么?先看一下
npm run release:win -- --dry-run

# 打包后要直接跑 win-unpacked 排障 / 冒烟?保留中间产物(默认删)
npm run release:win -- --keep-unpacked

# 双源发布(GitLab Generic Package + Release,可选同步 GitHub)
npm run publish:release
npm run publish:release -- --dry-run

# 或:打 tag 推到 gitlab remote,由 .gitlab-ci.yml 自动打包并双发
git tag v0.3.3 && git push gitlab v0.3.3
```

完整选项见 `npm run release -- --help`。

## 1. 整体设计

### 1.1 流水线六阶段

```
┌────────────────────────────────────────────────────────────┐
│                    npm run release:* [选项]                 │
├────────────────────────────────────────────────────────────┤
│                                                            │
│   Phase 1 · Preflight                                      │
│   ├─ Node ≥ 20                                             │
│   ├─ git status / 当前分支                                  │
│   ├─ 平台兼容(Win 主机不能直跑 Linux 包,自动走 Docker)    │
│   └─ --bump=*  → 改 package.json.version                   │
│                                                            │
│   Phase 2 · Code Quality                                   │
│   ├─ typecheck(三 tsconfig)                                │
│   ├─ ESLint + stylelint                                    │
│   └─ vitest run                                            │
│                                                            │
│   Phase 3 · Clean & Switch                                 │
│   ├─ clean out/ + node-pty/build(避免跨平台残留)           │
│   └─ install-app-deps --platform=<target>                  │
│      ↑ Windows 主机打 Linux 包时跳过(Docker 容器内 npm ci) │
│                                                            │
│   Phase 4 · Build                                          │
│   ├─ Windows: electron-vite build + electron-builder       │
│   └─ Linux:                                                │
│      ├─ Linux 主机: 直跑 npm run build:linux                │
│      └─ Win/Mac 主机: 走 Dockerfile.linux-build 隔离构建    │
│                                                            │
│   Phase 5 · Verify & Prune                                │
│   ├─ 扫所有 .node 文件,按 PE/ELF/Mach-O magic 判平台        │
│   ├─ 关键资源在位(app.asar / shell-hooks/ / context-menu)│
│   ├─ 体积合理(80 MB ≤ unpacked ≤ 500 MB)                 │
│   ├─ 输出每个安装器的 SHA256                                │
│   └─ Prune:默认删 {win,linux}-unpacked/ 中间产物           │
│      ↑ 必须在 verify 之后(verify 扫的就是 unpacked);      │
│        --keep-unpacked 可保留;verify 失败不删,产物保留供检查 │
│                                                            │
│   Phase 6 · Report                                         │
│   ├─ 产物清单 + 大小                                       │
│   └─ 下一步:CHANGELOG / commit / tag / push / GH release   │
│                                                            │
└────────────────────────────────────────────────────────────┘
```

### 1.2 核心设计决策

| 决策 | 选择 | 理由 |
|---|---|---|
| 哪个脚本是入口? | `scripts/release.mjs`,单文件总流水 | 用户不需要记 12 条命令,记一条 `release` 就够。每条 npm script 不超过一行 |
| 脚本语言? | Node.js `.mjs`,无新增依赖 | 跨 Win/Linux/Mac 一致;`node:fs` / `child_process` 够用,不引 `rimraf` / `cross-env` / `semver` 等(避免 AGENTS.md 1.2 边界 2) |
| 平台不在主机时怎么办? | Win 主机 → Linux 走 Docker;Linux 主机 → Win 不支持(本地报错) | Docker 隔离已经证明能根治 ISO-1;反向 Win-on-Linux 需要 wine,留给 CI |
| 失败时怎么办? | 任何阶段非零立即退出,产物保留供检查 | 不做"自动重试"或"自动清理失败产物"— 这两个都会掩盖根因 |
| unpacked 中间产物? | Verify 通过后默认删,`--keep-unpacked` 保留(2026-09-03 起) | unpacked 内容已完整封装进安装器,留着只占磁盘(Win 约 320 MB/版本;历史累积曾达 18 GB)。但 verify 扫的就是 unpacked,所以必须校验完再删;verify 失败时退出不删 |
| 跳过项的安全网? | 每个 `--skip-*` 都打黄色警告;`--skip-verify` 额外打红字 | 跳过是诊断用的,不是常态。让作者每次跳过都看到警告 |

## 2. 三层防御回顾(为什么有 verify 这步)

ISO-1 工单的核心教训是:**electron-builder 没报错 ≠ 产物没问题**。打包过程的成功只意味着"我把文件塞进了 .exe / .deb",不意味着"塞进去的文件平台正确"。

所以本流程在三个不同层级各设防御:

```
┌────────────────────────────────────────────────────────┐
│                    源头:node_modules                   │
│   build/Release/pty.node 跨 Win/Linux 共用同一路径,     │
│   每次切平台都会被覆盖                                   │
│                                                        │
│   防御 1 (Phase 3):清 native + install-app-deps        │
│      --platform=<target>  目标平台 ABI 编译             │
└────────────────────────────────────────────────────────┘
                            ↓
┌────────────────────────────────────────────────────────┐
│             中游:electron-builder staging               │
│   默认把 node-pty 整个子树打进每个包                     │
│                                                        │
│   防御 2 (electron-builder.yml):afterPack staging filter │
│      按目标 platform/arch 剔除错平台二进制(ISO-2)       │
└────────────────────────────────────────────────────────┘
                            ↓
┌────────────────────────────────────────────────────────┐
│                  下游:打包后的 .exe / .deb             │
│   即使前两层都失误也别让用户拿到坏包                     │
│                                                        │
│   防御 3 (Phase 5):verify-artifacts.mjs 扫所有 .node    │
│      用 magic bytes 判平台,不匹配 = 立即失败            │
└────────────────────────────────────────────────────────┘
```

三层独立,任一层失效另两层兜得住。详见 `docs/issues/iso-1-cross-platform-build-pollution.md`。

## 3. 各阶段细节

### 3.1 Phase 1 · Preflight

**做什么**:
- 读 `package.json` 拿当前版本
- 检查 Node 版本 ≥ 20(Electron 31 硬要求)
- `git status --porcelain`:有未提交改动时打黄字警告(不阻塞)
- `git branch --show-current`:显示当前分支
- 如果有 `--bump=*`:计算新版本号并写入 `package.json`

**版本号策略**(`--bump`):

```
当前 0.1.0-beta.9 + --bump=patch       → 0.1.1-beta.0
当前 0.1.0-beta.9 + --bump=minor       → 0.2.0-beta.0
当前 0.1.0-beta.9 + --bump=major       → 1.0.0-beta.0
当前 0.1.0-beta.9 + --bump=prerelease  → 0.1.0-beta.10
当前 0.1.0       + --bump=prerelease   → 0.1.1-beta.0
当前 0.1.0-beta.9 + --bump=none(默认)→ 0.1.0-beta.9
```

**手工版本号修改**也支持 — 直接编辑 `package.json.version`,然后跑 `npm run release` 不带 `--bump`。

**不做什么**:
- ❌ **不自动 commit**:`--bump` 只改 `package.json`,不 `git add`、不 `git commit`。CHANGELOG 是 prose,自动化反而容易写错
- ❌ **不阻塞 dirty git**:让作者自己决定。文档里反复警告但不卡

### 3.2 Phase 2 · Code Quality

**做什么**:
- `npm run typecheck`(三 tsconfig 串行)
- `npm run lint`(ESLint)
- `npm run lint:css`(stylelint)
- `npm test`(vitest run)

**跳过策略**:
- `--skip-typecheck` / `--skip-lint` / `--skip-tests` 各自独立
- 黄字警告,但不阻塞

**已知失败处理**:
- 截至 2026-05-20,`css-var-fallback.test.ts` 因 Catppuccin 主题 CSS 变量遗漏 fallback 而失败
- 修这个的工单单独走,**不**用 `--skip-tests` 当成长期解决方案

### 3.3 Phase 3 · Clean & Switch

**做什么**:
- `node scripts/clean.mjs --out --native`:清 `out/` 与 `node_modules/node-pty/build/`
- 按目标平台跑 `electron-builder install-app-deps --platform=<target> --arch=x64`

**矩阵**:

| 目标 \ 主机 | Windows | Linux | macOS |
|---|---|---|---|
| `--win` | switch:win | 报错(需 wine) | 报错 |
| `--linux` | 跳过(Docker 自己 ci) | switch:linux | 跳过(Docker) |

**为什么 Windows 主机打 Linux 包要跳过 switch?**
- Linux 包在 Docker 容器内构建,容器有自己的 `node_modules`(来自 `npm ci`)
- 主机的 `node_modules` 不进容器(`.dockerignore` 拦)
- 切平台只对"主机直接 electron-builder"路径有意义

### 3.4 Phase 4 · Build

**Windows 路径**:
```
electron-vite build → out/{main,preload,renderer}/
electron-builder --win --x64 → release/${version}/{Marina-Setup.exe, Marina-Portable.exe, win-unpacked/, latest.yml, *.blockmap}
                                                     ↑ win-unpacked/ 是打包 staging,Verify 通过后默认删除(--keep-unpacked 保留)
```

**Linux 路径(主机是 Linux)**:
```
electron-vite build → out/...
electron-builder --linux deb rpm AppImage --x64 → release/${version}/{Marina-*.deb, *.rpm, *.AppImage, linux-unpacked/, latest-linux.yml}
                                                                       ↑ linux-unpacked/ 同样在 Verify 通过后默认删除
```

**Linux 路径(主机非 Linux)**:
```
node scripts/build-linux-docker.mjs:
  1. docker build -f Dockerfile.linux-build -t marina-linux-build:local .
  2. docker run --rm -v "${PWD}/release:/build/release" marina-linux-build:local
     ↑ 容器内 CMD = npm run build:linux
```

#### 3.4.1 Linux 主机原生构建(无 Docker,FEX 实证 2026-09-20)

当目标机是 Linux 且**没有 Docker** 时,不需要 `build-linux-docker.mjs` —— 直接在
Linux 机上原生构建即可。FEX(`192.168.5.100`, Ubuntu 26.04,也是本仓 GitLab 所在机)
上跑通过的完整流程:

```bash
# 1) 取源码。用 tag 而非分支,保证与已发布版本严格对应
git clone --depth 1 --branch v0.3.3 \
  https://fexlagame.top:4812/aitool/marina.git ~/.cache/marina-build/0.3.3
cd ~/.cache/marina-build/0.3.3

# 2) 装依赖。注意:linux-x64 没有预编译,node-pty 在这一步被系统 node 编译
#    (链接 libnode.so)——所以下一步必须重编,不能直接构建
npm ci

# 3) node-pty 按 Electron 头强制重编(0.3.4 起必须;不重编 = libnode 污染)
npx @electron/rebuild@4.2.0 -f -w node-pty \
  -v "$(node -p "require('electron/package.json').version")"

# 4) 构建。注意两个 FEX 特有的点(见下)
npx electron-vite build
npx electron-builder --linux deb AppImage --x64 --config.npmRebuild=false

# 5) 校验(ISO-1 门禁 + libnode 依赖检查,与 Windows 侧同一脚本)
node scripts/verify-artifacts.mjs --version=0.3.3 --strict
```

**FEX 上的三个已知坑**(每条都实测踩过):

| 坑 | 现象 | 处理 |
|---|---|---|
| `rebuild-node-modules` 挂起 | electron-builder 卡在 0% CPU、无网络 | 加 `--config.npmRebuild=false`。这一步只做冗余重编;真正的 node-pty 编译由上面的 @electron/rebuild 步骤负责 |
| `pty.node` 链接 `libnode.so` | 装包机器没有 libnode 时 daemon 起不来,报错还伪装成 \"Cannot find module './prebuilds/linux-x64/.../pty.node'\"(实际是 dlopen 失败;node-pty 只抛最后一个候选路径) | 根因:install-app-deps 见 node-pty 带 prebuilds 目录会静默跳过重编,留下 npm 生命周期用系统共享库版 Node 编的产物。处理:构建前 `npx @electron/rebuild@4.2.0 -f -w node-pty -v <electron版本>` 按 Electron 头强制重编(头文件 electronjs.org/headers 直连可达,npmmirror 不托管);verify-artifacts 的 ldd 门禁兑底 |
| 缺 `rpmbuild` | `--linux rpm` 直接失败 | FEX 无 rpmbuild,**只出 deb + AppImage**;要 .rpm 得先 `apt install rpm` 或走 `Dockerfile.linux-build` |
| 缺 `desktop-file-utils` | `.desktop` 校验跳过 | 只影响 `desktop-file-validate` 校验,不阻塞产出 |

**注意:在 GitLab 所在机(FEX)上构建会留下约 1.3 GB/版本 的构建目录**
(`node_modules` ~740 MB + `release/` ~503 MB,其中 `linux-unpacked` ~314 MB)。
该目录在 `~/.cache/`,**不在 GitLab 备份范围内**,但占的是同一块磁盘。发完版可按需清理,
或加 `--keep-unpacked` 的反面:构建后删掉 `release/<version>/linux-unpacked/`。

**上游校验和对比**:`publish-release.mjs` 上传时按 `file_sha256` 判断幂等 ——
内容一致才跳过,内容变了(如补传平台后重算的 `sha256sums.txt`)则删远端旧文件再传。
所以"先发 Windows、后补 Linux"这种增量发布是安全的。

详见 `Dockerfile.linux-build` 顶部注释 + `docs/issues/iso-1-cross-platform-build-pollution.md` §"修复 3"。

### 3.5 Phase 5 · Verify & Prune

**Prune(2026-09-03 起)**:verify 通过后,默认删 `release/${version}/{win,linux}-unpacked/`。顺序不变量:prune 必须在 verify 之后(verify 扫的就是 unpacked);verify 失败时立即退出、不删,产物保留供检查。需要直接跑 unpacked 排障 / 冒烟时加 `--keep-unpacked`。

**检查项**:

1. **二进制平台一致性**
   - 扫 `release/${version}/{win,linux}-unpacked/` 下所有 `*.node`
   - 读前 16 字节判 PE / ELF / Mach-O / FAT
   - Windows 包不能含 ELF 或 Mach-O;Linux 包不能含 PE 或 Mach-O;macOS 包不能含 PE 或 ELF

2. **ELF 依赖纯净度(Linux 包,0.3.4 起)**
   - 对 Linux 包内每个 .node 跑 `ldd`,出现 `libnode.so` 依赖即失败
   - 背景:系统共享库版 Node 编译的原生模块会链接 libnode.so;Electron 内嵌
     Node,产物里不允许有这个外部依赖(0.3.3 的 pty.node 中招,装到无 libnode
     的机器上 daemon 起不来)

3. **关键资源在位**
   - `resources/app.asar` 文件
   - `resources/shell-hooks/` 目录
   - Windows 额外:`resources/context-menu/` 目录(MSIX 等)

4. **体积合理**
   - 下限 80 MB(< 这个数说明产物缺失)
   - 上限 500 MB(> 这个数说明漏过滤)
   - `--strict` 模式下超上限算失败,默认算警告

5. **安装器输出**
   - 每个 `Marina-*.exe / .deb / .rpm / .AppImage` 的大小 + SHA256
   - `.blockmap` 跳过 hash(它本身就是 hash 文件)

**机器可读输出**:
```
node scripts/verify-artifacts.mjs --json > verify-report.json
```

JSON 含每个包的完整 `nodeBinaries` 数组,可被 CI 解析。

### 3.6 Phase 6 · Report

**输出**:
- 各阶段耗时
- 产物清单与大小
- 下一步提示(仅在 `--bump=*` 时显示)
  - 改 CHANGELOG.md
  - git add + commit + tag + push
  - 在 GitHub Releases 上传

## 4. CI 化路径(GitLab 主路径 + 可选 GitHub Actions)

**当前分发策略(2026 起)**:**自建 GitLab 为 CI 与主发布源,GitHub Releases 同步双发**。

仓库根 `.gitlab-ci.yml` + `scripts/publish-release.mjs` 已落地(tag `v*` 触发)。

### 4.1 GitLab CI(自建,推荐)

```
tag v0.3.x
  → quality:linux   (typecheck / lint / test,marina-linux runner 原生 Node)
  → build:linux     (runner tag: marina-linux,原生构建 + verify --strict,无 Docker)
  → build:windows   (runner tag: marina-windows;未就绪期间为手动任务)
  → publish:release (Generic Package + GitLab Release;有 GH_TOKEN 则同步 GitHub)
```

**一次性配置**:

1. 注册 runner(两台都是 **shell executor**):
   - **Linux(FEX,2026-09-14 已注册)**,tag `marina-linux`。用户级 systemd 服务
     (`systemctl --user status gitlab-runner`,runner 二进制在 `~/.local/bin`)。
     **原生构建,不需要 Docker** —— 宿主机需 Node ≥ 20、g++/make/python3
     (node-pty 编译),构建命令与 §3.4.1 原生构建完全一致。
   - **Windows**,tag `marina-windows`(尚未注册)。shell 必须是 **PowerShell**(job 的
     `before_script` 用了 PowerShell 语法做 tag/version 校验);机器需装 Node 20、
     Python 3、VS Build Tools 2022(node-pty 原生编译)。
     未就绪期间 `build:windows` 是 tag 流水线里的手动任务,publish 不等它 ——
     **Linux 先发**:tag 推送即发 deb/AppImage;Windows 包产出后由
     `publish-release.mjs` 幂等补传(按 file_sha256 比对,已有且一致的自动跳过)。
2. Settings → CI/CD → Variables(**项目级**,不要写进 job 的 `variables:`,
   job 级会覆盖项目级):
   - `GITLAB_TOKEN` — **必填**;project access token,scope 需含 `api` + `write_repository`。
     `CI_JOB_TOKEN` 权限不足,不能替代。
   - `GH_TOKEN` — 可选,GitHub classic PAT(`repo`);不配则只发 GitLab
   - `GITHUB_OWNER` / `GITHUB_REPO` — 可选,默认 `fexla` / `marina`
   - `GITLAB_URL` / `GITLAB_PROJECT_ID` — **不用配**,由 CI 预定义变量
     (`CI_SERVER_URL` / `CI_PROJECT_ID`)映射
3. 发版:先按 §3 本地 bump + CHANGELOG,再 `git tag v<version>` 推到 gitlab remote

**产物校验(ISO-1 门禁)**:两个构建 job 都在产出后立刻跑
`verify-artifacts.mjs --strict` —— Windows 侧由 `release.mjs` Phase 5 调用,
Linux 侧在构建 job 内单独跑一次(扫 `release/<v>/linux-unpacked/`)。校验失败即
job 失败,不会进入 publish 阶段。

**产物落点**:

| 源 | 位置 |
|---|---|
| GitLab | Generic Package `marina/<version>/*` + Release `v<version>` |
| GitHub | Releases `v<version>`(同步) |

**下载链接必须用 API 路径(实测结论,2026-09-20)**:

Release 的资产链接由 `publish-release.mjs` 生成为
`https://<host>/api/v4/projects/<id>/packages/generic/marina/<version>/<file>`,
**不要**用网页路径 `https://<host>/<ns>/<project>/-/packages/generic/...`。

在自建实例上实测:项目虽为 public,网页路径匿名访问返回的却是
**GitLab 登录页(HTTP 200 + text/html)**,用户从 Releases 页点链接会看到 "Sign in";
API 路径匿名即可下载(HTTP 200 + `application/octet-stream`,安装器首字节为 `MZ`)。
代价是链接里带项目数字 id,换来的是可直接下载。

**本地手动双发**(不经 CI):

```bash
# 配好 GITLAB_URL / GITLAB_PROJECT_ID / GITLAB_TOKEN,可选 GH_TOKEN
npm run release:win          # 或 release:linux / release:all
npm run publish:release
npm run publish:release -- --dry-run   # 先看会传什么
```

### 4.2 GitHub Actions(可选镜像)

若还要在 GitHub.com 上直接跑构建(自建 GitLab 之外的备用流水线),可参考:

```yaml
# .github/workflows/release.yml
name: Release
on:
  push:
    tags: ['v*']
jobs:
  windows:
    runs-on: windows-latest
    steps:
      - uses: actions/checkout@v4
      - uses: actions/setup-node@v4
        with: { node-version: '20' }
      - run: npm ci
      - run: npm run release:win -- --strict --skip-typecheck --skip-lint --skip-tests
      - uses: actions/upload-artifact@v4
        with:
          name: marina-windows
          path: release/

  linux:
    runs-on: ubuntu-latest
    steps:
      - uses: actions/checkout@v4
      - run: docker build -f Dockerfile.linux-build -t marina-linux-build:ci .
      - run: mkdir -p release && docker run --rm -v "$PWD/release:/build/release" marina-linux-build:ci
      - uses: actions/upload-artifact@v4
        with:
          name: marina-linux
          path: release/

  publish:
    needs: [windows, linux]
    runs-on: ubuntu-latest
    if: startsWith(github.ref, 'refs/tags/v')
    steps:
      - uses: actions/download-artifact@v4
        with: { path: release, merge-multiple: true }
      - uses: actions/setup-node@v4
        with: { node-version: '20' }
      - uses: actions/checkout@v4
      - run: node scripts/publish-release.mjs --version="${GITHUB_REF_NAME#v}"
        env:
          GITLAB_URL: ${{ secrets.GITLAB_URL }}
          GITLAB_PROJECT_ID: ${{ secrets.GITLAB_PROJECT_ID }}
          GITLAB_TOKEN: ${{ secrets.GITLAB_TOKEN }}
          GH_TOKEN: ${{ secrets.GITHUB_TOKEN }}
```

不需要 macOS runner 直到 V2.0 启用 mac 包。

**签名仍不在 CI 内做**(KI-002):证书到位后在 Windows job 注入 `CSC_LINK` / `CSC_KEY_PASSWORD`,再考虑自动更新。

## 5. 故障排查

### 5.1 Phase 2 卡在 typecheck

**症状**:`tsc --noEmit` 报错。

**通常原因**:
- TypeScript 版本升级后语法变化
- 三个 tsconfig 中某个的 `include` / `exclude` 漏了

**修法**:跑 `npx tsc --noEmit -p tsconfig.node.json`(或 preload / web)逐个看;不要直接 `--skip-typecheck`。

### 5.2 Phase 3 install-app-deps 卡很久

**症状**:`electron-builder install-app-deps` 长时间无输出,最终 fail。

**通常原因**:
- 国内网络拉 Electron 二进制慢 / 失败
- node-gyp 找不到 Python / Visual Studio Build Tools(Windows)
- node-gyp 找不到 gcc / make(Linux,不会发生因为 Docker 镜像已装)

**修法**:
- 设镜像:`set ELECTRON_MIRROR=https://npmmirror.com/mirrors/electron/`(Win)/ `export ...`(Linux)
- Windows 上确保装了 Visual Studio Build Tools 2022 + Python 3.10+

### 5.3 Phase 4 Docker build 失败

**症状**:`docker build` 在 `RUN npm ci` 步骤 fail。

**通常原因**:
- Docker daemon 没启动
- `package-lock.json` 与 `package.json` 不同步
- 主机 `node_modules` 进了容器(`.dockerignore` 没拦住)

**修法**:
- `docker info` 检查 daemon
- 主机跑一次 `npm install` 同步 lockfile
- 看 `.dockerignore` 是否在仓库根(不是子目录)

### 5.4 Phase 5 verify 报"cross-platform-binary"

**症状**:`verify-artifacts.mjs` 输出 `✗ [cross-platform-binary] ...node 是 ELF (Linux),但 win 包应该是 PE (Windows)`。

**通常原因**:
- `electron-builder.yml` 的 `afterPack` 钩子被移除或执行失败
- `scripts/filter-node-pty-after-pack.cjs` 不认识新的平台 / 架构 / 上游目录结构
- `node_modules/node-pty/build/Release/pty.node` 来自上次错平台构建

**修法**:
- 确认 `electron-builder.yml` 仍注册 `filter-node-pty-after-pack.cjs`
- 看打包输出是否出现 `[afterPack:node-pty] ... kept=<目标>`；未知目标必须 fail closed
- 跑 `npm run switch:<target>` 重置 native 后重打，再执行 `verify-artifacts --strict`

### 5.5 Phase 5 报"size-too-small"

**症状**:unpacked 体积 < 80 MB。

**通常原因**:
- `electron-vite build` 失败但 `electron-builder` 仍然跑了
- `out/` 在 build 之前没干净,只 build 了一部分

**修法**:`npm run clean` + `npm run release:<target>`(不带 `--no-clean`)。

### 5.6 verify 通过了但用户跑安装器仍报 .node 加载失败

**症状**:`Cannot find module ... .node` 或类似。

**通常原因**:
- node-pty `prebuilds/` 被过滤太狠(把当前平台也排除了)
- Electron ABI 不匹配(install-app-deps 跑成了 plain Node ABI 而不是 Electron's)

**修法**:
- 看 `[afterPack:node-pty] kept=...` 是否对应当前 platform/arch
- 删 `node_modules/`,从头 `npm install`(重跑 postinstall = install-app-deps)
- 看 `release/${version}/<plat>-unpacked/resources/app.asar.unpacked/node_modules/node-pty/` 实际有哪些 .node
  ↑ 默认打包流程会删 unpacked;要看它需 `npm run release:<target> -- --keep-unpacked` 重新打包,或从安装器解出
