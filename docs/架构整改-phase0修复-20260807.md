## 1. 背景

核心诊断(复核):Marina 从单机 Electron 演进到多窗口 / 远程 daemon / terminal-side agent 后,旧的 **window-centric transport interface** 没同步升级为 **client capability interface**。主线 = 把 routing + authorization + lifecycle 做成显式、穷尽、可测试的深模块。

本批按"代码问题直接修"(deepseek-v4-flash worker 并行,主 agent 设计 spec + 整合验证)推进,落地了方向明确的 5 个修复。剩余偏设计/大重构,文末列出。

## 2. 已完成修复(5 commit)

### 2.1 H1 · WORKSPACE 路由 + ADR-029 · `5190643`
**问题**:7 个 `WORKSPACE_*` 命令误归 `local-control`(`protocol.ts` 的 `LOCAL_CONTROL_COMMANDS_SET`),远程窗口的 workspace 读写发到客户端本地 main 而非所连 daemon,workspace 快照静默脱节。
**根因**:ADR-024(`protocol.ts:429` 注释)把 workspace 归为"客户端本地 daemon 状态",但远程窗口连的 daemon 上的 session,其 workspace 属该 daemon 的 backend,应走 `backend-data`。依据:`docs/软件定义书.md:2304-2309 / 2363-2368`("远程数据归 daemon,appearance 是唯一本地例外")。
**改动**:
- `protocol.ts`:7 个 `WORKSPACE_*` 从 `LOCAL_CONTROL_COMMANDS_SET` 移除(改走 backend-data)。`SETTINGS_GET/UPDATE_APPEARANCE` 保留(合法本地例外)。
- ADR-024 的 routing 部分废止,补 **ADR-029** 记录"workspace 跟 session 归属的 backend(daemon)"。ADR-024 的 35+ 引用都是持久化机制语义,未动。
- H3(routing 部分):`getCommandRouting` 从 fail-open(漏列默认 backend)改 **fail-closed**(未知 channel 抛错);新增 `COMMAND_CHANNEL_VALUES` 穷尽集。
- 测试:`protocol.test.ts` 完整性测试(每个 `COMMAND_CHANNEL` 恰好分类)+ WORKSPACE round-trip(返回 backend-data)。

### 2.4 H4 · quiesce 状态机 · `5592e08`
**问题**:退出流程先 shutdown session/scheduler 再异步 flush,期间 IPC/WS/HTTP 仍接新工作,新工作可能落在 shutdown/flush 之后。1s flush 预算不是问题,"期间还接新活"才是。
**改动**:
- `app-lifecycle.ts` 扩展为显式状态机:`running → quiescing → flushing → stopped`。`setQuitting` 内部映射 `enterQuiescing`。
- Transport gate(四处):`ipc.ts` `dispatchCommand` + 本地 `ipcMain.handle` + `transport-ws` message handler + `file-panel-service` HTTP ingress,quiescing 后拒新工作(返回 `{ok:false,error:{code:'Quiescing'}}`)。
- `index.ts` before-quit 有序化:`enterQuiescing` → 停 WS/HTTP ingress → shutdown session/scheduler → `enterFlushing` → flushAll(1s 预算保留防卡死)→ `enterStopped`。
- 测试:`app-lifecycle.test.ts`(状态机 6 测)+ `ipc.test.ts`(gate 拒绝:`enterQuiescing()` 后 `dispatchCommand` 返回 Quiescing)。

### 2.5 H2 · file-panel 命令 owner 校验 · `51fcc5f`
**问题**:file-panel/gallery 的 IPC handler(get/open/open-path/show/close/read/read-image/gallery)不校验调用者是不是 session owner,任何 client 能读/改别的 session 的文件面板。违反软件定义书"owner 独占内容"。
**owner 语义(已核实)**:`session.ownerWindowId` 字段名虽叫 windowId,但实存 owner 的 **clientId**(本地=windowId,远程 WS=握手 id,见 `remote-daemon.ts:15-16` 注释)。校验 = `ownerWindowId === envelope.windowId`。
**改动**:
- `ipc.ts` 新增 `requireFilePanelOwner(sessionManager, sessionId, requesterId)`:owner 不符抛 `makeIpcError('NotOwner')`。9 处 handler 入口调用。**遵循项目既有 `FileTreeService.requireOwner` 模式**,未单独建 authorization.ts(更符合现有风格)。
- `FilePanel.tsx` 加 `waitForClaim(sessionId)`:消除"renderer 乐观接管(owner 仍 null)→ mount 立即拉取 → 命中 NotOwner"的 race。与 FileTreePanel/GitPanel 同模式。
- 测试:`ipc.test.ts` +116 行,双 client 场景(非 owner 拒绝、owner 通过)。

## 3. 关键设计发现:file-panel 事件广播是有意的(未改)

复核 H2 建议"file-panel/Git/file-tree 事件 owner-only(`sendEventTo` owner)"。但读 `ipc.ts:2648-2662` 注释,发现开发者**有意**广播,理由明确:

> 面板状态是 per-session 元数据,用户切到别的终端时该 session 会变 orphan(ownerWindowId=null)...但它的面板状态变更必须持续更新——否则 orphan 期间的更新被「无 owner 即丢弃」吞掉,用户下次切回该终端看到的还是旧面板。PTY 字节流才需要定向 owner...面板/git 这类小元数据广播给所有窗口无副作用(各自存进 per-session map,不显示就不读)。

且 **command-panel / code-block 已是 owner-only**(`ipc.ts:2668-2694`,命令输出敏感确实定向了)。

**判定**:file-panel/Git/file-tree 广播是**设计权衡**(orphan 更新送达 vs 最小授权),不是代码 bug。复核的 owner-only 建议与此冲突。**未擅自改**——这是需要定夺的设计决策。H2 实际状态:**命令层(主动操作)已堵住;事件层维持有意设计**。

## 4. R01 调研结论:error.code 跨 IPC 丢失(留给 T08)

renderer 读错误码读不到,两道序列化墙都剥自定义属性:
- Electron IPC 的 structured clone(WHATWG spec §2.7.5):对 Error 有专门分支,只保 name/message,不走通用属性遍历。
- `contextBridge.exposeInMainWorld`:第二道序列化墙,再剥一次。

证据:`TerminalView.tsx:789` 注释、`store.tsx:1110` 与 `App.tsx:116` 防御式读 code、`dispatchCommand`(`ipc.ts:470`)WS 路径已用 `{ok,error:{code}}` envelope 绕过(说明开发者已知)。

**推荐修复(T08,未做)**:`registerHandle` 返回 `{ok:true,data}|{ok:false,error:{code,message,details?}}` envelope,`invoke` 解包。与现有 `dispatchCommand` 对称,单点改 `ipc.ts`+`preload`,75+ handler 自动受益。**但 preload→renderer 过 contextBridge 仍剥属性,invoke API 可能要改为返回 discriminated union(而非 throw)**——这是 T08 的设计含量。
